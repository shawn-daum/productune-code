# Structure — planner-tables

The shape of an explanation follows the KIND of thing being explained. In user-chat, name the kind first, then write in its shape:

| kind | shape |
|---|---|
| fork — a decision with 2+ paths | the one option · pros · cons · recommendation table plus a one-line why (the decision table the contracts require) |
| change — a mechanism or rule is changing | an as-is / to-be table, two columns, one row per thing that moves |
| consequence — what is gained, what breaks | a numbered list with the count stated up front ("three things change:") |
| comparison — n items against shared criteria | a table: rows are the items, columns the criteria |
| answer — a direct question | one or two plain sentences. Never a table |

- The last row is the safeguard: this profile is not "always a table" — it is one shape per kind, and a yes/no wrapped in a table reads worse than the sentence.
- Anything outside these rows: prefer a few short sentences to a dense option matrix.
- Cells stay plain-worded — the `audience` body decides the vocabulary inside them, `form` decides how the prose around the table reads.
- This shapes HOW you say things, never WHAT you decide.

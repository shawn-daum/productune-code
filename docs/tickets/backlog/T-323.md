## Request

**productune 제품 기능**: productune이 오케스트레이트하는 사용자 프로젝트의 **git 브랜치 워크플로를 자동 관리**한다. (사용자 결정 2026-07-07, 적용 범위 = 제품 기능. Define 진입 시 PRD 먼저.)

### 브랜치 모델
- **`main`** — repo의 prime/default 브랜치. **배포된 "최종 버전" 코드만**, 청결. `docs/`(PRD·tickets·wiki) **미포함**.
- **`dev`** — 최신 버전의 개발용 통합 브랜치 (main 직전 스테이징).
- **`<version>`** (v1·v1.1·v2…) — 버전별 작업 브랜치. "버전 시작 = 그 브랜치에 상주".

### 승격 흐름
- 버전 시작 → 해당 `<version>` 브랜치에서 작업(코드 + docs).
- **첫 버전**: 배포되면 → `main`으로 승격.
- **첫 실배포 이후**: 다음 버전부터 `<version>` → `dev` → (배포) → `main`. dev가 릴리즈 게이트.

### docs를 main에서 제외 (목표: 배포 코드 청결, main pull한 사람이 ticket을 바로 안 봄 — 브랜치 파보면 보이는 건 허용)
- **채택 방향 = A안(파생 미러)**: `main`을 **코드 전용 파생 브랜치**로 취급. productune의 promote/release 스텝이 배포 시 `docs/`를 제외하고 코드만 `main`에 sync. docs/PRD/tickets는 dev·version에만 상주. (doctrine #6 "도구가 파생물 유지"와 정합.)
- 함의: `main`은 dev의 단순 조상이 아님(ff 불가, 항상 promote 스텝 경유). release 미러로 typical.
- (기각) B안 브랜치별 .gitignore + 머지 경로 제외 — 크로스브랜치 divergent 파일 머지 마찰 큼.

## Acceptance

- (Define/PRD 진입 시 상세화) productune이 위 브랜치 모델을 사용자 프로젝트에 대해 생성·유지: 버전 시작 시 version 브랜치 체크아웃/상주, dev·main 승격 커맨드, 배포 시 코드-전용 main sync(docs 제외).
- 첫 배포는 version→main 직접, 이후 버전은 version→dev→main.
- `main` pull 시 `docs/` 부재(코드만). 다른 브랜치에는 docs 상주.
- 기존 contracts.md의 "trunk + 버전 브랜치 없음" 규칙과의 관계 정리 (이 기능은 제품이 관리하는 사용자 프로젝트 git 모델 — productune 팀 내부 규율과 별개인지, 통합인지 PRD에서 결정).

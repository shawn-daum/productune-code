# T-P4-055: High-fidelity mockup preview — PreviewTab 디자인 스펙

**Round**: phase4-r4  **Stage**: design  **Status**: todo  **Assignee**: pdt-designer  
**Design ref**: [docs/artifacts/design-direction.md §4.3.2](../../design/design-direction.md)  
**Estimated complexity**: L3  **Risk flags**: electron-webview, path-resolution

> 4종 디자인 산출물(`system.md` / `flow.md` / `screens/*.excalidraw.json` / `mockups/*.html`) 중 **mockup HTML** 의 main-pane viewer 스펙.  
> T-P4-046 dispatcher 에서 `preview` tab type 은 현재 `PlaceholderTab` — 본 ticket 이 실제 `PreviewTab` 컴포넌트 디자인 스펙을 정의하고, 그 결과를 impl ticket 에 전달한다.

## §1 Background

`design-direction §4.3.2` 에 따르면 `preview` tab type 은 `prev-chrome (URL bar + Local/Vercel toggle) + prev-body (iframe placeholder)` 로 명시됐으나, T-P4-046 구현 범위에서 `prev-body` 는 `PlaceholderTab` 으로 처리됐다.

한편 Designer 가 emit 하는 4종 산출물 중 `docs/artifacts/<slug>/mockups/*.html` (hi-fi mockup HTML) 은 현재 **GUI 에서 열람 수단이 없다**. 설계 리뷰 / 사용자 승인 flow (T-P4-054 경로) 에서 mockup HTML 을 main-pane 에서 바로 볼 수 있어야 한다.

따라서 `preview` tab type 의 실체를 **mockup HTML renderer** 로 재정의한다. Local/Vercel live URL 렌더링은 `browser` tab type 으로 이미 커버되므로 중복 없음.

## §2 Scope

### A. PreviewTab 래퍼 — `PreviewTab.tsx`

| 영역 | 역할 |
|---|---|
| `prev-toolbar` (36px) | 파일 picker 드롭다운 + zoom controls + 오른쪽: mapping-ref 토글 버튼 |
| `prev-body` (flex 1) | mockup HTML 렌더 영역 (iframe / Electron `<webview>`) |
| `prev-mapping` (선택적 우측 패널 280px) | mockup → code 매핑 참조 표. 기본 collapsed. |

레이아웃: `flex-col` 전체 높이. `prev-toolbar` 고정, `prev-body` flex-grow. `prev-mapping` 은 토글 시 right side-by-side 분리 (`flex-row`).

### B. Mockup file source 해석 순서

렌더링 대상 파일 경로 해석 우선순위:

```
1. props.mockupPath  (openTab() 호출 시 명시적 경로 — 우선)
2. docs/artifacts/v0.4/productune/mockups/*.html  (default slug = "productune")
3. docs/artifacts/<activeSlug>/mockups/*.html  (active ticket slug 기반)
```

- 해석 실패 또는 파일 없음 → `EmptyState` 컴포넌트:  
  icon `FileImage` (lucide), headline `"mockup 파일이 없습니다"`, description `"docs/artifacts/<slug>/mockups/ 경로에 HTML 파일을 추가하세요."`, CTA `"Explorer 열기"` (ghost sm).

### C. Mockup file picker

```
┌─ prev-toolbar ────────────────────────────────────────────────────┐
│ [FileImage 16] [dropdown: mockup.html ▼]  [–] [100%] [+] [⊡ fit] │ [□ mapping]
└────────────────────────────────────────────────────────────────────┘
```

- 드롭다운 = `Select` (shadcn 패턴, `body-sm` 14px). 항목: `<filename>.html` 목록 (알파벳 정렬).  
- 파일 변경 → iframe/webview `src` 교체. 전환 중 `prev-body` 에 `Loader2 pdt-spin` (center) 노출, 로드 완료 시 숨김.  
- 파일 0개 → picker 비활성 + `EmptyState` 노출.

### D. Zoom / Fit-to-window controls

| 컨트롤 | 동작 | 시각 |
|---|---|---|
| `–` (ZoomOut) | 10% 단위 축소. 최소 25% | `ghost sm` 버튼, lucide `ZoomOut` 16px |
| zoom level label | `50%` / `75%` / `100%` / `150%` / `200%` — 클릭 시 100% 즉시 복귀 | `caption` 13px `code` 폰트, min-width 40px, text-center |
| `+` (ZoomIn) | 10% 단위 확대. 최대 200% | `ghost sm` 버튼, lucide `ZoomIn` 16px |
| `⊡` (fit) | `scale` 재계산 — `min(containerW / iframeW, containerH / iframeH)` | `ghost sm` 버튼, lucide `Maximize2` 16px. active 시 `primary-500` tint |

zoom 구현: iframe `transform: scale(Z)` + `transform-origin: top left`. `prev-body` overflow hidden. container resize 시 `fit` 상태면 자동 재계산 (`ResizeObserver`).

### E. Mockup → code 매핑 참조 표

`prev-mapping` 패널 토글 버튼: `ghost sm`, lucide `Table2` 16px, 라벨 `"매핑"`. active 시 `primary-500` tint.

패널 내부:
```
┌─ prev-mapping 280px ──────────────────────┐
│ "Mockup → Component 매핑"  title-3 600    │
│ ─────────────────────────────────────      │
│ HTML element ID     Component name         │
│ #rp-hdr             RightPanelHeader       │
│ #rp-msgs            MessageList            │
│ #status-bar         StatusBar              │
│ ...                                        │
│ (항목 없음 시 caption "매핑 정의 없음")    │
└────────────────────────────────────────────┘
```

- 매핑 데이터 source: `docs/artifacts/<slug>/mockup-map.json` (선택 파일; 없으면 empty state).  
- `mockup-map.json` 스키마:

```json
{
  "file": "mockup.html",
  "mappings": [
    { "id": "rp-hdr", "component": "RightPanelHeader", "note": "35px header" }
  ]
}
```

- 표: `caption` 13px. 행 hover = `gray-800/40` bg. 클릭 행 = 해당 element 에 iframe `postMessage({ highlight: "#id" })` (opt-in; mockup HTML 미지원 시 무시).

## §2 Mockup preview format

### 2.1 Format 후보 비교

| 후보 | pros | cons | productune 적합 |
|---|---|---|---|
| **A. HTML/CSS static** | 로컬 only / 디자인 시스템 token 직접 활용 / git diff / Mermaid + Excalidraw 와 같이 `docs/artifacts/<slug>/` 트리 안 자리 | 인터랙션 X (정적) / 화면당 한 파일 | **default 채택** |
| B. 외부 image (PNG/JPG/WEBP) | AI 이미지 generator 결과 직접 첨부 가능 / 사용자가 Figma export 직접 import | non-canonical 명시 필수 (텍스트가 픽셀로 박힘) / token 분리 X / 색약 보정 X | **보조 채택** (allowed, marked) |
| C. Figma embed iframe | 디자이너 협업 자연스러움 | 외부 의존성 (Figma 계정) — Phase 4 PRD 의 "외부 서비스 의존 X" 위반 (ROADMAP 컨텍스트 표) | **거부** |
| D. Designer 직접 생성한 SVG | 로컬 / token 활용 가능 | HTML 대비 typography / layout 표현력 낮음 (특히 한글 fallback) | 옵션 X (specialty) |
| E. 별도 web service (Storybook 등) | rich preview | productune 외부 의존 / Phase 4 PRD 위반 | **거부** |

### 2.2 채택 (default = A, allowed = B)

**Primary — A. HTML/CSS static**.
- 경로: `docs/artifacts/<slug>/mockups/<screen-key>.html` (po-loop.md §2B' `T-NNN-d` 정합).
- 한 파일 = 한 화면. inline `<style>` 또는 sibling `<screen-key>.css`. 외부 asset
  X (font / image / cdn).
- design system token 을 inline CSS 변수로 미러 (`--accent: #FF6B2B` 등) — `system.md`
  과 1:1 매핑.
- viewport `<meta>` + responsive breakpoint 1 개만 (desktop default, dense mode).
- 한국어 + 영문 보호어 (PRD/stage enum) 그대로 — i18n 카탈로그 미반영. mockup 은
  "느낌" 합의용이지 카탈로그 source 아님.

**Secondary — B. 외부 image (allowed)**.
- 경로: `docs/artifacts/<slug>/mockups/<screen-key>.{png,jpg,webp}`.
- 사용 case: (i) AI image generator (GPT image / Midjourney) 가 빠른 분위기
  sketch 제공, (ii) 사용자가 직접 reference 첨부, (iii) HTML 로 표현 어려운 시각
  (그라데이션 / 일러스트 / 사진).
- **명시 marking 필수** — 같은 디렉터리에 `<screen-key>.note.md` 또는 HTML 안
  `<!-- non-canonical visual agreement only -->` 주석. preview viewer (T-P4-046
  `preview` tab) 가 banner 표시 (§3.4).

**Mermaid / Excalidraw 와의 정합**.
- Mermaid: `docs/artifacts/<slug>/flow.md` — flow chart only, mockup 책임 X.
- Excalidraw: `docs/artifacts/<slug>/screens/<screen-key>.excalidraw.json` — wireframe.
- HTML mockup: `docs/artifacts/<slug>/mockups/<screen-key>.html` — hi-fi. **같은
  `<screen-key>`** 가 wireframe ↔ mockup 매핑 keying (PO 가 같은 화면의 두 단계
  비교 가능).

**예시 디렉터리 구조** (단일 slug 안):
```
docs/artifacts/<slug>/
├── system.md                           # design system (T-NNN-a)
├── flow.md                             # mermaid (T-NNN-b)
├── screens/
│   ├── onboarding-step-0.excalidraw.json   # wireframe (T-NNN-c)
│   └── workspace-shell.excalidraw.json
└── mockups/
    ├── onboarding-step-0.html              # hi-fi html (T-NNN-d, default)
    ├── workspace-shell.html
    └── workspace-shell.note.md             # non-canonical marker (optional)
```

### 2.3 화면 선정 (key screens 기준)

"key screens" 정의 — 본 ticket 의 Acceptance "현실감 있는 mockup" 의 범위.
- **first-run path** 한 화면 이상 (예: onboarding step 0, empty WorkspaceShell).
- **happy path 의 핵심 화면** 1 ~ 3 개 — feature 의 가장 자주 보이는 화면.
- **위험 화면** (error / blocked / destructive confirm) 중 1 개 — §1.5.4 Feedback
  / §1.5.5 Escape 톤 합의 위해.

key screen 수는 4 ~ 6 개 권장. 무한정 늘리지 않는다 — mockup 은 합의 도구지
스펙 도구 아님.

### 3.3 사용자 검토 / 승인 사이클

T-P4-054 (디자인 산출물 → 사용자 검토/승인) 의 sub-flow.

```
Designer emits 4 artifact (system / flow / wireframe / mockup)
  │
  ▼
PO surface (user's lang):
  "design artifacts ready — 4 files: system, flow, N wireframes, N mockups.
   review and proceed to Build?"
  │
  ├─ 사용자 "OK / 이대로 진행"  → Build stage 진입 (Phase 3)
  │
  ├─ 사용자 "수정: 특정 화면 톤 다르게"
  │      → Designer 재호출 (resume session)
  │      → 해당 mockup file 만 patch (다른 3 artifact 영향 X)
  │      → 다시 surface
  │
  ├─ 사용자 "수정: 색 / spacing 전체"
  │      → Designer 가 system.md patch → mockup 일괄 재생성
  │      → 다시 surface
  │
  └─ 사용자 "mockup 생성 실패 / 어떻게 보일지 모르겠다"
         → fallback: wireframe + system + flow 3 종만으로 승인 (Acceptance 8 정합)
         → Build 진입 후 mockup 은 impl 단계 design-compliance gate (Gate 3) 에서 합의
```

**Gate 위치** — 본 사이클은 po-loop.md "Uniform phase-transition gate" 의 Phase
2→3 boundary 안. PO 가 `pending_gate` 에 4 artifact list + mockup 우선 검토
prompt 작성. 사용자 응답 = approval / modification / silence.

### 3.4 Mockup 생성 실패 / 미지원 graceful fallback

본 ticket Acceptance "이미지 생성 실패/미지원 시에도 design 승인 계속" 정합.

| 실패 case | Designer 처리 |
|---|---|
| HTML mockup 작성 시간 부족 / 우선순위 | wireframe + system + flow 3 종 emit, mockup 은 다음 Designer 호출에 (또는 R4 dogfood 처럼 impl 후 합의 — Gate 3) |
| 외부 image generator 미연결 | HTML mockup default 로 진행 (B 옵션 자체 skip) |
| 사용자가 "느낌 너무 추상" | mockup 우선순위 ↑, wireframe 보조로 강등 |
| Designer 가 시각 표현 어려운 영역 (3D / 비디오) | persona spec 의 `external_tool_recommendation` 으로 GPT image / DALL-E / Spline / Runway 추천 + prompt 동봉. 결과 = B 옵션 (외부 image) 으로 첨부 |

### 4.4 Approval CTA (T-P4-054 통합)

본 viewer 가 T-P4-054 (디자인 산출물 검토/승인) flow 의 한 surface.
- `pendingGateId` 가 props 로 전달되면 footer 의 approval row 활성.
- 3 CTA:
  1. **primary** — `design 승인하기` (Build 진입). i18n `preview.mockup.action.approve`.
     - 클릭 → confirm modal (§1.5.5 destructive 가 아니므로 Esc 허용) → PO IPC
       `phase:approveGate(pendingGateId)` → `pending_gate` clear + Phase 3 시작.
  2. **secondary** — `수정 요청`. i18n `preview.mockup.action.requestRevision`.
     - 클릭 → 자유 텍스트 modal (어디 / 어떻게 수정) → PO IPC
       `phase:requestRevision(pendingGateId, note)` → Designer resume.
  3. **ghost** — `wireframe 만으로 진행`. i18n `preview.mockup.action.skipMockup`.
     - graceful fallback (§3.4) — mockup 합의 없이 Build 진입. ticket 의 risk_flag
       에 `mockup-skipped` 메타 부착 (Gate 3 design-compliance 가 catch).
- §1.5.1 Few Things — primary + secondary + ghost = 3 CTA 이지만 ghost 는 escape
  hatch (out-of-decision). 화면 안 primary intent 2 개 정합.

### 4.5 §1.5 self-check (본 컴포넌트 신규 — design-system §1.5.6 정합)

| # | sub-rule | 본 컴포넌트 정합 |
|---|---|---|
| 2-1 | Few Things | banner / viewer / footer / approval = 4 region. action 핵심 2 (approve / revision). ghost 1. ≤ 2 만족 |
| 2-2 | 익숙한 경험 | iframe 렌더 + prev/next 화살표 + open-in-browser = browser preview convention 차용 |
| 3-1 | Predictability | mockup 없음 → §8.9 Empty pane recipe (icon `Image`, headline `mockup not provided`, CTA `regenerate via Designer`) |
| 3-2 | Feedback | iframe 로딩 시 `--health-info` spinner, approval click 즉시 disabled + spinner, error 시 `--health-error` + retry |
| 3-3 | Escape | tab close X (`X` icon) + Esc + banner dismiss + ghost CTA "wireframe 만으로 진행" 4 출구 |

### 4.6 IPC + 보안

mockup HTML 은 사용자 제출 / Designer 생성 — script 실행 가능. iframe 은 sandbox
필수.
- `<iframe sandbox="allow-same-origin"` 만. `allow-scripts` 미부여 (mockup 은 정적
  CSS 만). HTML 안 `<script>` 가 있어도 실행 X.
- Electron `webPreferences.webSecurity: true` 유지. `nodeIntegration: false`. file://
  스킴 접근은 main process 에서 read → renderer 로 string blob 전달.
- preview 영역 내부 link 클릭 (`<a href>`) 은 main process 가 intercept 후
  `shell.openExternal` 로 default browser 위임 (renderer 안에서 navigation X).

## §8 Risks / Anti-patterns

| risk | 완화 |
|---|---|
| mockup 의 한국어 텍스트 / 가짜 데이터가 production 카피로 leak | banner 항상 노출 + 보호어 어휘 검사 (§10) + impl 단계 i18n 카탈로그 베이스라인 분리. mockup 텍스트는 카탈로그 source X |
| 외부 image (B) 의 텍스트가 픽셀로 박힘 → 색약 / 번역 / OCR 불가 | `<key>.note.md` 에 본문 영문 + 한글 텍스트 mirror + banner `--health-warn` 격상 |
| mockup HTML 안 `<script>` 가 실행되어 renderer XSS | iframe `sandbox` 속성 `allow-same-origin` 만 — `allow-scripts` 미부여. main process file:// read → string blob 전달 |
| Designer 가 system token 무시하고 inline hex 박음 → mockup ↔ system.md 정합 깨짐 | self-check §3.2 #1 + R5 enhancement 로 token lint (OQ-7) |
| mockup 의 시각 톤이 너무 매력적 → 사용자가 mockup 을 spec 으로 오인 | banner 항상 노출 + Acceptance 의 "non-canonical" 명시 + impl 단계 Gate 3 (design-compliance) 의 mockup ↔ actual UI diff 노출 |
| mockup 만 보고 wireframe / system / flow 건너뜀 | T-P4-054 approval flow 가 4 artifact 모두 노출 보장 (single Build gate). single artifact partial approve X |
| 같은 slug 안 wireframe / mockup `<screen-key>` 불일치 | self-check §3.2 #2 + impl 단계 viewer 가 sibling discovery 시 mismatch 경고 |

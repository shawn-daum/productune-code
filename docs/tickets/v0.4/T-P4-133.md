## §1 Request

**Origin**: T-P4-124 OQ-K gap candidate G9 — pdt-qa already has access to 7 Playwright MCP tools at runtime, but productune-specific usage patterns are not codified. Every QA smoke dispatch re-derives: which selectors to use, which assertions to make, how to feed results back into the dev-qa-auto-loop envelope, when to capture screenshots, how to detect console errors. A `qa-playwright-smoke` skill closes this gap.

**What exists today**:
- Playwright MCP tools: `browser_navigate`, `browser_click`, `browser_type`, `browser_screenshot`, `browser_evaluate`, `browser_wait_for_selector`, `browser_get_console_logs` (or equivalent).
- `docs/qa/` directory with QA playbook artifacts.
- dev-qa-auto-loop pattern: PO dispatches pdt-qa with `browser_url` + `verify_url` + ticket context; QA navigates, asserts, returns structured result.

**Gap**: no skill doc telling pdt-qa *how* to apply those tools to productune GUI specifically — tab selectors, panel layout, expected element ids, assertion thresholds, screenshot naming, loop-exit criteria.

### A2. Skill body covers 5 pattern sections

1. **Selector conventions** — productune GUI data-testid / role-based selector hierarchy:
   - Tab navigation: `[data-tab="<tabKey>"]` or `role=tab` + `name=<label>`
   - Ticket rows: `[data-ticket-id="<id>"]`
   - Panel areas: `[data-panel="main"]`, `[data-panel="side"]`
   - InfoPopover trigger: `[aria-label="<field> 전체 보기"]`
   - Fallback: CSS class selectors only when data-* absent (note: fragile, flag)

2. **Assertion checklist** — per smoke run:
   - Page load: no `role=alert[aria-live=assertive]` with error text within 3s
   - Tab render: target tab content visible (`role=tabpanel` non-empty)
   - Key elements: ≥1 data row visible when data expected; 0 rows visible when empty state expected
   - Console errors: `browser_get_console_logs` → assert zero `error`-level entries (warn OK)
   - Screenshot: capture after assertions, name = `<ticket_id>-<tab>-<yyyymmdd>.png`

3. **dev-qa-auto-loop envelope integration** — structured QA result schema:
   ```
   qa_result: { pass: bool, tab: str, assertions: [{name, pass, detail}],
                console_errors: int, screenshot_path: str, notes: str }
   ```
   PO reads `qa_result.pass` for loop-exit decision. `pass: false` → PO routes back to pdt-developer with `qa_result.assertions` as failure context.

4. **Screenshot capture timing** — capture *after* all assertions complete (not mid-flow). One screenshot per smoke run unless multi-tab flow (one per tab). Store under `docs/qa/screenshots/` with ticket-scoped filename.

5. **Console error capture pattern** — call `browser_evaluate` to drain `window.__productune_errors__` if instrumented, else rely on `browser_get_console_logs`. Any `error` entry → `pass: false` regardless of visual assertion outcomes (console errors are silent regressions).

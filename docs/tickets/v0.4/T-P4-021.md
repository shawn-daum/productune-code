## §1 Goal

ticket 단위 작업이 git 에 자동으로 보존되는 mechanism. 사용자는 "자동저장" 어휘만
보고, 내부적으로는 T-P4-020 에서 만든 ticket worktree 안 `git commit` 이 일어난다.

**Scope 한정 (OQ-2 정합)**: trigger 시점 = **ticket md frontmatter 의 `status` /
`qa_status` / `qa_loops` 변경 시점만**. ROADMAP line 146 의 원문 "페르소나 turn 종료
+ 상태 변화" 보다 보수적 — turn 종료마다 commit 하면 noise 가 많고, 상태 변화 없는
turn (예: PO routing 만 한 case) 은 의미 있는 mile-stone 이 아니다.

T-P4-020 worktree API + T-P4-065 fs-watcher 위에 **얇은 autosave manager + IPC**
한 층 추가. 외부 어휘 (`commit` / `push` / `sha`) 사용자 노출 0.

## §2 Trigger 시점 (OQ-2 정합 핵심)

### 2.1 감지 대상 — ticket frontmatter 3 필드

`docs/tickets/<version>/T-NNN.md` frontmatter 중:

| field | trigger 의미 |
|---|---|
| `status` | `todo` → `in-progress` → `done` / `blocked` / `abandoned` |
| `qa_status` | `pending` → `passed` / `failed` / `static-pass` |
| `qa_loops` | `0` → `1` → `2` ... (loop 증가) |

위 3 필드 중 **어느 하나라도 직전 snapshot 과 다르면 autosave 1 회 trigger**.

### 2.2 trigger 에 포함하지 **않는** 변경

- `title` / `description` / `request` / `acceptance` / `notes` 등 본문 변경
- `started_at` / `completed_at` / `duration_min` 같은 mechanical timestamp
- Persona Activity 표 row 추가 (이건 status 변경과 함께 자주 일어나므로 status 변경이
  대표 trigger 가 된다)
- frontmatter 의 `branch` / `worktree_path` 필드 (T-P4-020 의 mechanical update)

이유: 본문 / mechanical 필드는 사용자 의도 mile-stone 이 아니라 PO sed/append.
autosave 의 의미 = "사용자가 알아볼 만한 상태 변화 시점에 작업 보존".

### 2.3 fs-watcher 재사용

T-P4-065 sub-f 가 이미 land 한 `useTicketScan` 의 fs-watcher (`docs/tickets/**`,
debounce 500ms) 를 **main 프로세스 측에서 동일하게 sub** 한다. autosave manager 는
renderer 의 ticket scan 과 **독립적인 second subscriber** — UI scan 과 race 없이
독립 동작.

> 구현 분기 (sub-a 결정): main 측에 fs-watcher 두 번 두기 보다, **T-P4-065 의 main
> 측 watcher 가 두 채널 (`tickets:changed` IPC event + `autosave:onFrontmatterChange`
> 내부 emitter) 로 fan-out** 하는 방식이 깔끔. 본 design 은 후자 권장.

### 2.4 debounce + dedupe

- fs-watcher 단의 500ms debounce 는 PO 가 mechanical sed burst (예: status +
  Persona Activity row 동시 수정) 를 1 회로 묶기 위함. autosave 도 같은 debounce
  사용 → 1 변경 = 1 commit 보장.
- diff-empty (`git status --porcelain` 빈) 시 commit skip. autosave snapshot 만
  갱신 + trace = "변경 사항 없음 — 저장 생략" inline 로그.

## §3 Commit message 포맷

### 3.1 패턴 (OQ-T021-2 권장 — 상태 기반)

```
T-P4-<id> [<changeReason>: <before>→<after>] <summary>
```

예:
- `T-P4-021 [status: in-progress→done] design plan land — 12 sections + 4 OQ`
- `T-P4-035 [qa_status: pending→passed] static-pass after 2 loops`
- `T-P4-046 [qa_loops: 1→2] retry — fix split-pane focus regression`

### 3.2 OQ-T021-2 — 포맷 선택

ROADMAP line 146 원문은 `T-NNN [persona/turn N] <summary>` (turn 기반). OQ-2 결정
이후 turn 종료 자체는 trigger 가 아니므로 turn 정보가 message 의 first-class 가
되면 의미가 어긋난다. **상태 기반 포맷이 OQ-2 정합 + 사용자 [버전 히스토리]
(T-P4-023) 의 자연어 카드 변환에도 직관**.

> 사용자 결정 필요 (§11). default 권장 = 상태 기반.

### 3.3 summary 합성

- `summary` = 80 chars cap (R2 plan §5.4 정합).
- source 우선순위: (a) ticket 의 마지막 Persona Activity row 의 `Result` 컬럼 →
  (b) 없으면 ticket title 80 chars truncated → (c) 없으면 fallback `"<changeReason>
  trigger"`.
- 이모지 / 컬러 이모지 제거 (memory rule: lucide-react default, 컬러 emoji 금지).

### 3.4 commit author

- `git config user.name` / `user.email` 가 이미 set 돼 있으면 그대로.
- 없으면 fallback `productune-autosave <noreply@productune.local>` + status bar
  inline trace "git author 가 비어 있어 autosave 가 임시 author 로 저장했어요"
  (자연어, 1 회 noti).

## §4 Hook / Manager 구조

### 4.1 위치 (T-P4-020 의 `git-workflow/` 옆)

- `packages/core/src/git-workflow/autosave.ts` — 본 ticket 의 신규 모듈
  - `class AutosaveManager { detectChange, commit, getSnapshot, setSnapshot }`
  - frontmatter diff + commit 책임
- `packages/core/src/git-workflow/worktree.ts` (T-P4-020 land 됨) — 재사용
  (worktree path 조회)
- `packages/core/src/git-workflow/rules.ts` (T-P4-024) — `autosaveTriggers` 필드
  read (현 단계 default 만, Phase 5 lock 까지는 enum 강제 X)

### 4.2 호출 흐름

```
fs-watcher (main, T-P4-065)
  → tickets:changed event (renderer fan-out)
  → autosave:onFrontmatterChange (internal, main 측)
       ↓
  AutosaveManager.detectChange(projectDir, ticketId)
       ↓ (diff vs snapshot)
  changeReason ∈ {status-change, qa-status-change, qa-loops-change, none}
       ↓ (≠ none 이면)
  AutosaveManager.commit(projectDir, ticketId, changeReason, before, after)
       ↓
  git commit in worktree → { committed: true, sha }
       ↓
  IPC event: autosave:committed → renderer inline trace
```

### 4.3 base worktree noop 분기

- ticket frontmatter 의 `worktree_path` 가 비어 있거나 base worktree (`<projectDir>`
  자체) 면 commit skip. 단 사용자가 직접 [자동저장] 트리거를 호출하는 경로 (현
  단계 없음, 추후 manual save 메뉴) 가 생기면 **§5 친절 모달** trigger.
- fs-watcher 자동 trigger 면 silent noop + `autosave:noop` trace (사용자 모달 X,
  status bar inline 만).

## §6 IPC API

### 6.1 main → renderer (event)

```ts
// preload bridge
onAutosaveCommitted(cb: (ev: AutosaveCommitted) => void): Unsubscribe
onAutosaveSkipped(cb: (ev: AutosaveSkipped) => void): Unsubscribe

interface AutosaveCommitted {
  projectDir: string
  ticketId: string
  changeReason: 'status-change' | 'qa-status-change' | 'qa-loops-change' | 'manual'
  before: string  // 직전 값 (예: 'in-progress')
  after: string   // 변경 후 값 (예: 'done')
  sha: string     // 내부용 (사용자 노출 X)
  summary: string // 80 chars cap
  committedAt: string // ISO
}

interface AutosaveSkipped {
  projectDir: string
  ticketId: string
  reason: 'diff-empty' | 'base-worktree' | 'snapshot-init' | 'manager-error'
  detail?: string
}
```

### 6.2 renderer → main (command, 후속용 manual trigger)

```ts
api.autosaveTrigger(projectDir: string, ticketId: string, reason: 'manual')
  : Promise<{ committed: boolean; sha?: string; skipReason?: string }>
```

MVP 단계에선 호출 site 없음 — 본 IPC 는 contract 만 미리 마련 (T-P4-067 후속 인라인
trace + manual save 메뉴 발행 시 재사용).

### 6.3 IPC 어휘 정책

- IPC 채널명 / event payload field 는 영문 보호어 (`commit`, `sha`) 그대로. 사용자
  화면 노출 path 에서만 한국어 자연어로 변환.
- 변환 위치 = §8 trace 메시지 합성 (renderer 측).

  empty 로 1 회 noop commit) 가능. project 오염 0.
- 단점 "다중 머신 sync X" — autosave 가 머신별 ticket worktree 에 묶이므로 어차피
  cross-machine 동작 X. snapshot 만 share 할 이유 없음.

### 7.3 schema (A 안)

// ~/.productune/state/autosave-snapshots/<sha1(projectDir)>.json

  "projectDir": "/Users/.../proj-x",
  "tickets": {

## §9 회귀 / 정합

### 9.1 T-P4-020 worktree 정합

- autosave 는 **반드시 T-P4-020 worktree path 안** 에서 `git commit` 실행. 직접
  `<projectDir>/.git` 가 아닌 worktree 의 `.git` (worktree 는 internal `.git` 파일
  pointer).
- worktree 가 없으면 (사용자가 T-P4-020 land 전 만든 legacy ticket) → §5 noop +
  silent skip (manager-error 아님, `worktree-missing` reason 추가 권장).

### 9.2 T-P4-024 `git-rules.json` 정합

- `autosaveTriggers.events` field 가 이미 `["ticket-status-change"]` default 로
  land 됨 (Phase 5 lock UI). 본 ticket 은 해당 default 값을 **read-only 로 존중**.
  사용자가 직접 file 편집해 다른 값을 넣어도 MVP 는 무시 (Phase 5 에서 enum 확장).
- rules.ts 의 `loadRules()` 호출은 의무 — 미래 enum 확장 시 manager 가 수정 없이
  대응.

### 9.3 T-P4-065 fs-watcher 정합

- 새 watcher 추가 금지. 기존 main 측 watcher 가 두 채널 fan-out (§2.3).
- debounce 500ms 동일 — autosave 가 별도 debounce 하면 fs-watcher 와 race.

### 9.4 T-P4-067 inline trace 패턴 정합

- BackgroundTaskSegment 의 trace row 컴포넌트 재사용. autosave 도 일반 background
  task 와 동일한 시각 격 (one-line row, time + icon + message).
- 아이콘 = lucide `Save` 또는 `CheckCircle2` (`--icon-sm`, `--text-muted`).
  컬러 이모지 금지 (memory rule).

### 9.5 [버전 히스토리] T-P4-023 정합

- T-P4-023 가 git log 를 자연어 카드로 변환할 때 본 ticket 의 commit message
  포맷 (`T-P4-<id> [<reason>: <before>→<after>] <summary>`) 을 parser 가 인식해
  "T-P4-021 의 상태가 '진행 중' → '완료' 로 변경됐어요" 류 자연어로 풀어낼 수 있게
  포맷 안정성 유지.
- T-P4-023 발행 시 본 design 의 §3 패턴 참조 의무.

## §13 Risk / 관찰점

1. **fs-watcher race** — T-P4-065 의 watcher 가 renderer ticket scan 과 autosave
   manager 둘 다 fan-out 받을 때 timing. 권장 = autosave 가 항상 renderer scan
   **이후** 처리되도록 main 측 순서 보장. (debounce 같은 500ms 이므로 자연스러움)
2. **snapshot init 무한 loop 위험** — 신규 ticket 의 첫 scan 시 snapshot 없음 →
   "diff" 로 인식 → commit → snapshot 갱신. 1 회는 OK. 단 commit 실패 시 snapshot
   안 갱신되면 next watcher tick 에서 또 시도 → loop. 권장 = snapshot 갱신을
   commit success 와 분리 (manager-error 시에도 snapshot 갱신, commit 만 retry
   queue).
3. **base worktree 사용자 직접 ticket 편집** — base worktree 에서 사용자가 ticket
   md 를 손으로 편집하면 fs-watcher 가 잡지만 autosave 가 base 라서 noop. 사용자
   변경분이 git 에 안 남는 risk. 권장 = T-P4-020 의 base-dirty 모달이 이미
   "작업공간에서 시작해주세요" 안내하므로 그 경로로 흡수. 본 ticket 추가 액션 X.
4. **commit message summary fallback chain** — Persona Activity row 의 Result
   컬럼이 80 chars 초과 시 truncate. truncate 위치 한국어 char boundary 깨질
   가능성 → grapheme-aware truncate 권장.

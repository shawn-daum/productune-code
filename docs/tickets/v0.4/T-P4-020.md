## §2 Worktree 생성

### §2.1 위치 + 구조

```
<project>/
  .git/                       ← single git repo (worktree 들이 공유)
  .productune/
    config.json
    git-rules.json            ← T-P4-024 schema, 본 plan 의 r/w source
    worktrees/                ← 본 plan 의 신규 디렉터리
      T-P4-020/
        .git                  ← file (gitdir pointer — git worktree 표준)
        packages/...          ← project source tree (branch 별 격리)
        docs/...
      T-P4-021/
      ...
  .gitignore                  ← `.productune/worktrees/*` 등록 (T-P4-058 hygiene 정합)
```

worktree 내부의 `.git` 은 **file** (gitdir pointer) — `git worktree add` 가
표준으로 발급. directory 아님. PO 가 페르소나 호출 시 cwd 를 worktree path 로
설정 (PO 책임).

### §2.2 생성 시점 (PO 흐름 통합)

**Trigger**: ticket md 발행 시점. PO 가 `docs/tickets/<round>/T-NNN.md` mechanical-write
완료 후 → `worktree:create(projectDir, ticketId, slug, type, riskFlags)` IPC 호출.

```
PO ticket 발행 sequence:
  1. ticket md frontmatter 결정 (id / type / risk_flags / slug)
  2. ticket md mechanical-write (현행)
  3. NEW: IPC `worktree:create(...)` 호출
  4. IPC 응답 (worktreePath / branchName) → ticket md 의 `worktree_path:` / `branch:` field stamp (mechanical update — T-P4-020 ticket md L47 Acceptance 와 정합)
  5. po-state.json 의 `current_task.worktree_path` + `branch` set (Acceptance L46)
  6. 사용자 toast: "[T-NNN] 작업 공간이 준비됐어요."  (자연어 — `worktree` 어휘 X)
```

#### 실패 시 정책

- IPC 실패 (예: base branch dirty / git 명령 실패) → 사용자에게 자연어 모달:
  - 카피: "이 작업의 공간을 준비하지 못했어요. 변경되지 않은 다른 작업이 있을 수
    있어요. [다시 시도] / [건너뛰기]"
  - [건너뛰기] = ticket md 는 발행 유지 (rollback X). `worktree_path:` / `branch:`
    필드 = `null`. 자동저장 / 배포 게이트가 본 ticket 에서 동작 X — 사용자가
    Settings 의 "이 작업 공간 다시 만들기" CTA 로 재시도 가능 (Phase 5 candidate
    — 본 plan 영역 X, ticket md notes 에 trace).
  - [다시 시도] = 같은 IPC 재호출. base branch dirty 면 OQ-T020-2 정책 따라 stash
    / 확인 모달 / silent 실패 (§10 결정 후 확정).

## §3 Branch 명명

### §3.1 Pattern

```
<prefix><ticket-id>/<slug>
```

예:
- `feature/T-P4-020/ticket-worktree-base-branch`
- `fix/T-P4-067/chatpanel-restart-feedback`

(R2 §5.3 + T-P4-024 §2 schema 와 정합.)

### §3.2 Prefix 자동 분류

ticket md frontmatter 의 `type` / `risk_flags` 를 PO 가 IPC `args.type` 으로
전달. IPC 본체는 단순 mapping:

| ticket frontmatter | IPC `args.type` | prefix source |
|---|---|---|
| `type: fix` | `'fix'` | `gitRules.fixBranchPrefix` (default `'fix/'`) |
| `risk_flags` 에 `fix` 포함 | `'fix'` | `gitRules.fixBranchPrefix` |
| 그 외 (`type: impl`, `type: design`, ...) | `'feature'` | `gitRules.featureBranchPrefix` (default `'feature/'`) |

분류 책임 = PO (mechanical 단순 매핑). IPC 본체는 `args.type` 만 read.

#### prefix 변경 즉시 반영 정책 (T-P4-024 §5 inherit)

- Settings 의 `featureBranchPrefix` / `fixBranchPrefix` 변경 = **다음 ticket
  발행부터 적용**. 이미 발행된 ticket 의 branch 이름은 immutable.
- T-P4-024 Settings sub-tab 에서 "다음 ticket 부터 적용됩니다" inline note 노출.
  본 plan 영역 X (T-P4-024 spec).

### §3.3 Slug 처리

- ticket frontmatter `slug:` field 그대로 사용 (kebab-case 가정).
- 25 char cap (R2 §5.3 + 본 plan 정합).
- 25 char 초과 → 단순 right-truncate. 마지막 `-` 가 있으면 그 위치까지로 cut.
  사용자 노출 X (worktree directory 이름 만 영향).

### §3.4 Branch 이름 충돌

- IPC 본체가 `git rev-parse --verify <branchName>` 으로 사전 체크.
- 존재 시 suffix `-2`, `-3`, ... 자동 (`feature/T-P4-020/.../-2`).
- 충돌 발생 시 사용자에게 inline 알림 X (worktree 어휘 노출 회피). PO 에게
  IPC 응답으로만 trace.

### §4.2 hook 설치 시점

- 설치 결과 사용자 노출 X. 실패 시 dev mode trace 만.

### §4.3 hook 본문 (POSIX shell)

```sh
#!/bin/sh
# productune managed pre-push hook
# Source: T-P4-020 (https://...productune/docs/artifacts/v0.4/T-P4-020-ticket-worktree-base-branch-protection.md)
# Auto-generated. Edit `.productune/git-rules.json` to change protected list.

PROTECTED_BRANCHES="$(cat .productune/git-rules.json 2>/dev/null \
  | sed -n 's/.*"protectedBranches"[[:space:]]*:[[:space:]]*\[\([^]]*\)\].*/\1/p' \
  | tr -d '" ' | tr ',' '\n')"

# fallback when git-rules.json missing
if [ -z "$PROTECTED_BRANCHES" ]; then
  PROTECTED_BRANCHES="main"
fi

while read local_ref local_sha remote_ref remote_sha; do
  branch="${remote_ref#refs/heads/}"
  for protected in $PROTECTED_BRANCHES; do
    if [ "$branch" = "$protected" ]; then
      echo ""
      echo "  이 작업 줄기는 직접 보낼 수 없어요."
      echo "  배포 준비 단계를 거쳐 보내주세요."
      echo ""
      echo "  (대상 = $protected)"
      echo ""
      exit 1
    fi
  done
done

exit 0
```

#### 카피 결정 (자연어 / 어휘 노출 X)

- "직접 보낼 수 없어요" = `push` 어휘 회피 (R2 §1.2).
- "배포 준비 단계" = R2 §1.1 사용자 가시 어휘 (= [배포 준비], T-P4-022).
- "작업 줄기" = `branch` 어휘 회피 — sed 안 parse 한 raw branch 이름 ("$protected")
  은 trace 노출 OK (dev 도움). planner mode 와 dev mode 모두 동일 카피.
- jq 의존 X — POSIX sed 만 사용 (jq 없는 사용자 환경 fallback).

### §4.4 protectedBranches 자동 계산 (T-P4-024 §2.1.1 inherit)

- `git-rules.json.protectedBranches` 는 **display only field** (사용자 manual 편집 X).
- 실제 값은 schema r/w 시점에 자동 계산:
  - `useDevBranch: false` → `["main"]`
  - `useDevBranch: true` → `["main", "dev"]`
- hook 의 sed parse 도 이 자동 계산된 값을 source 로 사용.
- `useDevBranch` 토글 변경 시 = T-P4-024 schema write 후 hook 자동 재설치 (또는
  `git-rules.json` 자체를 sed 가 매번 read 하므로 재설치 불필요 — 본 plan 채택).
  즉 토글은 hook 본문 변경 X, hook 동작이 매번 fresh read.

### §4.5 hook 이미 존재 (사용자 별 hook 박혀있는 case) — **OQ-T020-1**

- 사용자 결정 받기. §10 참조.
- 현재 잠정 권고 (final stamp 전): **backup + 교체**. 이유:
  - append 는 두 hook 의 exit code 충돌 위험.
  - 사용자 명시 모달은 onboarding 시점에 사용자 인지 부담 ↑.

### OQ-T020-1 — pre-push hook 이미 존재 시 정책

### OQ-T020-4 — base branch 가 remote 와 mismatch 상태 (`git fetch` 안 한 case)

worktree 생성 시점에 local `main` 이 remote `origin/main` 보다 stale 한 경우의
처리. 새 worktree branch = local main 위에 분기되면 추후 push 시 conflict
가능성.

| 옵션 | 장점 | 단점 |
|---|---|---|
| **(a) pre-emptive `git fetch` 트리거** (designer 잠정 권고) | 정확한 base. push 시 conflict 위험 ↓. | 매 ticket 발행마다 network call (수 100ms). 오프라인 / rate-limit 시 실패. |
| (b) silent 진행 (local main 기준 worktree 생성) | 빠름. 오프라인 동작. | conflict risk 누적 — 사용자가 [배포 준비] 시점에 발견. |
| (c) 사용자에게 alert ("최신 변경을 받지 못했어요. 지금 받을까요? [지금 받기] / [건너뛰기]") | 사용자 통제. | onboarding 부담 ↑. 사용자가 "받기" 의미 모를 수 있음. |

**designer 권고**: **(a) pre-emptive `git fetch`**. 이유:
- 매 ticket 발행이 자주 발생하지 않음 (수 100ms cost 무시 가능).
- 오프라인 fallback = `git fetch` 실패 시 silent 진행 + dev mode trace.
- (c) 모달은 R2 §1.2 의 "받기" = `pull` 어휘 노출 risk — `fetch` 는 더더욱 X.
- Phase 5 candidate = "원격 동기 cooldown" 정책 (5 분 안 fetch 한 경우 skip).

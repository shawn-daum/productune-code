# T-P4-094: Ticket dashboard unknown-status fallback — 외부 project schema mismatch 시 ticket 사라짐 회피

## Background

사용자 dogfood (2026-05-12) — `paepyeong` (별 productune 사용 project) GUI 진입 시
ticket board 가 broken:

> 실제 paepyeong 폴더에는 21 개 ticket md 가 있는데 GUI ticket board 에는
> DONE 컬럼 7 개만 표시되고 나머지 14 개는 화면에서 완전히 사라짐.
> "필터에 맞는 티켓 없음" 같은 fallback 도 안 뜨고 그냥 컬럼 0 count.

**Root cause** — paepyeong 과 productune doctrine 간 status enum 불일치:

| project | status enum |
|---|---|
| paepyeong (현장) | `open` / `done` |
| productune doctrine (T-P4-065) | `todo` / `in-progress` / `review` / `done` / `blocked` / `abandoned` |

`TicketDashboardView.tsx` 의 `groupByStatus(tickets)` 는 ticket.status 를
group key 로 그대로 사용 (line 109-117):

```ts
function groupByStatus(tickets: Ticket[]): Record<string, Ticket[]> {
  const out: Record<string, Ticket[]> = {}
  for (const t of tickets) {
    const k = (t.status as Status) ?? 'todo'   // ← null/undef 만 todo, unknown string 은 그대로
    if (!out[k]) out[k] = []
    out[k].push(t)
  }
  return out
}
```

이후 render 는 `STATUS_ORDER` (5 enum) 의 column 만 만들고 `byStatus[s] ?? []`
로 lookup — `open` 같은 unknown key 의 bucket 은 어떤 column 도 read 하지
않음 → 화면에서 silent drop.

**즉시 land 한 fix** (본 ticket 밖, 별 project 측): paepyeong 의 14 개 ticket
md 에 `sed` 로 `status: open` → `status: todo` 일괄 migration. paepyeong
schema 정상화는 끝.

**본 ticket = productune GUI 측 robustness 보강** — 다른 project 가 schema
가 다르더라도 ticket 이 화면에서 사라지지 않게.

## Goal

productune GUI 가 임의 외부 project 의 ticket md 를 열었을 때:

1. **unknown status 의 ticket 은 절대 화면에서 사라지지 않는다.**
2. 화면이 schema mismatch 를 명시적으로 표시 (사용자가 "왜 ticket 이 안
   보이지?" 라고 의심하지 않도록).
3. productune 자체 schema (5 enum) 에는 회귀 없음.

## Scope

### A) `groupByStatus` 의 unknown fallback 정책

`packages/gui/src/components/workspace/TicketDashboardView.tsx` `groupByStatus`
함수 수정. unknown status key 처리 — OQ-T094-1 결정에 따라 한 가지 채택:

- **옵션 (a) `todo` 컬럼 단순 fallback**:
  ```ts
  const STATUS_SET = new Set<Status>(STATUS_ORDER)
  const k0 = (t.status as Status) ?? 'todo'
  const k = STATUS_SET.has(k0) ? k0 : 'todo'
  ```
  pro: 가장 적은 코드 변경. con: 사용자는 schema mismatch 가 있다는 사실 자체를 인지 못 함.

- **옵션 (b) `Other` 신규 컬럼**: `STATUS_ORDER` 끝에 `'other'` 추가 + i18n
  label 신규 (`Other` / `기타`) + column header 색상 회색 (neutral).
  pro: schema mismatch 가 화면에 명시. con: column 6 개로 늘어 mockup
  layout 변형 영향 (mockup audit 필요).

- **옵션 (c) banner + `todo` fallback 합성**: unknown bucket 발생 시 화면
  상단 warning banner 1 줄 ("Schema mismatch — N tickets shown under "todo"
  fallback. Check project doctrine.") + 내부 group key 는 `todo` 로 fallback.
  pro: 가시성 + 시각 정합 유지 둘 다. con: 가장 코드량 큼 + i18n key 신규.

**designer 권고** — **옵션 (c)**:
- (a) 는 silent fallback — 본 dogfood case 와 같이 사용자가 의심하지 않는
  실패 mode 를 만들 수 있음. UX §1.5.4 Feedback 위반.
- (b) 는 다른 project 가 정상이어도 항상 6 컬럼 — 단일 project / 단일
  doctrine 사용자가 column 늘어남에 confused.
- (c) 는 default behavior 는 (a) 와 동일 + abnormal case 만 banner 로
  surface — Few Things / Predictability 둘 다 만족.

dev 가 (c) 와 다른 선택을 한다면 본 ticket impl 단계에서 PO 에 escalate.

## Implementation notes

- `groupByStatus` helper 는 export 되어 있지 않음 (file-private). 옵션 (c)
  채택 시 unknown count 도 동일 helper 의 secondary return 으로 묶기 권고

  conditional render 에 사용.
- `STATUS_SET` 은 `STATUS_ORDER` 에서 파생하면 single SoT 유지 — magic
  string set 별도 정의 금지.
- `Status` type 자체 변경 X — 본 ticket 은 runtime fallback 만. type 정합
  은 T-P4-065 doctrine 의 5 enum 유지.

## DS / UX 점검 (§1.5)

- **Few Things**: banner 1 줄 / count 1 개 / link X — 최소 표면.
- **Familiar**: banner pattern 은 기존 `SessionHealthBanner` 와 동일 시각
  언어 (위쪽 thin row + neutral background + 좌측 dot).
- **Predictability**: 동일 ticket set 으로 진입 → 동일 banner state.
- **Feedback**: silent drop (현행) → explicit surface (개선).
- **Escape**: banner 자체 dismiss 필요 없음 (정보 surface only, 행동 강제 X).

옵션 (a) 채택 시 §1.5.4 Feedback 항목 violation — 사용자가 schema mismatch
인지 못 함. 본 가이드라인이 (c) 권고의 근거.

## Risk

- 외부 project 의 schema 가 매번 다양할 수 있음 — 본 ticket 은 status 만
  fallback. type / qa_status 등 다른 enum 의 mismatch 는 별 ticket 으로
  분리 (필요 시).
- (c) 채택 시 banner 가 매 진입마다 발화 — 사용자가 noise 로 느낄 수 있음.
  dismiss 기능은 본 ticket scope 외 (필요 시 후속 ticket).

→ version id 표기 룰 정합 (`v1` / `v0.1` 만) + paepyeong 등 legacy migration + onboarding / PO flow / ticket lint / UI rendering 전 영역 enforce.

## T-P4-095 design plan — Version id naming convention (project slug prefix 금지)

**Created**: 2026-05-12   **Author**: pdt-designer   **Round**: phase4-r4 (cleanup, R2 ticket land 후)
**Source**: user 2026-05-12 dogfood feedback — "버전 naming 도 규칙 필요하겠다. paepyeong-v1 X, v1 O"
**Related**: T-P4-086 (ticket↔version frontmatter migration precedent), PRD §10 versioning

### §1 Background

paepyeong project dogfood 중 사용자가 `paepyeong/.productune/po-state.json` 에서 `versions[0].id = "paepyeong-v1"` 발견. project slug 가 version id 앞에 prefix 로 박혀 있어 어휘 중복 + git tag / SemVer 친숙 패턴과 어긋남.

#### Root cause

- po-state.json `versions[].id` 생성 시점에 강제 schema / validator 없음.
- onboarding wizard / PO version-create flow 에 placeholder + 검증 가이드 X.
- ticket frontmatter `version:` field (T-P4-086 land) 도 동일 자유 입력 — 추후 같은 violation 재발 위험.
- 결과적으로 GUI 의 version pill 이 "paepyeong-v1" 그대로 노출 — 프로젝트 안에서 본인 slug 가 다시 보이는 어색함.

#### 사용자 정합성 관찰

- git tag 컨벤션 (`v1.0.0`) + SemVer (`MAJOR.MINOR.PATCH`) 친숙.
- 사용자는 project 컨텍스트 안에 이미 있음 — slug 를 version id 안에 반복할 이유 없음.
- 한 프로젝트 안에서 version id 가 유일하면 충분 (cross-project 비교 시점은 GUI 가 project name + version id 결합 표기 가능).

---

### §2 Naming rule (spec)

#### 형식

```
version id MUST match: ^v\d+(\.\d+)?$
```

허용:
- `v1`, `v2`, `v10`
- `v0.1`, `v0.2`, `v1.2`

금지:
- `paepyeong-v1` (slug prefix)
- `v1.0.0` (3-segment — 본 ticket 범위는 stable 2-segment 까지)
- `v1-rc`, `v1-beta` (pre-release suffix — 별 ticket)
- `version-1`, `1.0`, `V1` (대문자), `v1_0` 등 변형

#### Rationale (§1.5 self-check 정합)

| §1.5 원칙 | 적용 |
|---|---|
| Familiar | git tag / SemVer 표기 친숙 (`v1` / `v0.1`) |
| Few Things | regex 단일 (`^v\d+(\.\d+)?$`) — 분기 X |
| Predictability | 입력 즉시 valid/invalid 피드백 (regex match 직결) |
| Feedback | invalid 시 1줄 안내 ("버전 이름 형식: v1 또는 v0.1") |
| Escape | migration script `--dry-run` default + `--apply` opt-in (data 손실 회피) |

### §3 Where enforced

#### A. Onboarding wizard (project create 시 first version)

**Path**: `packages/gui/src/components/onboarding/` (또는 project-create wizard 의 version-init step).

- first version 생성 UI 의 input field placeholder = `v1`
- 입력 변경 시 즉시 regex 검증 → invalid 시 input 아래 1줄 inline 안내 (`--text-warning` 토큰):
  > 버전 이름 형식: v1 또는 v0.1
- valid 시 [다음] 버튼 활성
- default value = `v1` (사용자가 그대로 진행 가능)

#### B. PO version-create flow

**Path**: PO doctrine — `packages/core/po/sections/lifecycle.md` (Version transition spec) + `~/.productune/sections/lifecycle-mechanics.md`.

- PO 가 `versions[].id` 신규 push 전 regex 검증 (jq 또는 inline shell).
- 사용자가 자연어로 "v2 시작" / "v0.3 갈게" 같은 표현하면 PO 가 그대로 stamp.
- 사용자가 invalid id (예: "round-2", "다음 버전") 제시 시 PO 가 1줄 안내 후 confirm:
  > 버전 이름은 v1 또는 v0.1 형식으로 부탁드려요. "v2" 로 진행할까요?
- 검증 통과 후에만 `versions[]` append.

#### C. Ticket frontmatter `version:` field

**Path**:
- `packages/core/po/sections/tickets.md` (Required frontmatter spec 갱신)
- ticket-md schema 검증 linter (T-P4-057 패밀리 또는 신규 lint hook)

- ticket frontmatter `version:` field 도 동일 regex 적용.
- 예외 (`legacy/phase3-fixes` 등 artificial id) 는 frontmatter 에 명시적 allowlist comment 또는 별 field (`legacy: true`) 로 표기.
- CI / pre-commit lint 에서 violation 발견 시 fail + 안내 메시지.

#### D. Migration — legacy id strip

**Path**: `packages/gui/scripts/migrate-version-id.mjs` (신규).

**왜 별 script** — 기존 `migrate-ticket-version.mjs` 는 ticket md 에 version field 추가 (stamping). 본 script 는 기존 id 값 자체를 변환 (transform). 책임 분리 + idempotent 보장 단순화.

**동작**:

1. **scan**:
   - `<projectDir>/.productune/po-state.json` 읽고 `versions[].id` 추출.
   - `<projectDir>/docs/tickets/**/*.md` 의 frontmatter `version:` 값 추출.
2. **detect violations**:
   - regex `^v\d+(\.\d+)?$` 미일치 항목 수집.
   - legacy artificial id (`legacy/...`) 는 skip (별 정책).
3. **propose mapping**:
   - `<slug>-v<n>` 패턴 매칭 → `v<n>` strip.
   - 일반 violation (`round-2`, `version-1` 등) → manual override 요구 (stderr warn + skip).
4. **dry-run (default)**:
   - 매핑 표 stdout:
     ```
     paepyeong-v1   →   v1   (po-state.json)
     paepyeong-v1   →   v1   (docs/tickets/v0.4/T-P4-100.md)
     ...
     stripped: N · skipped: M · manual-needed: K
     ```
5. **`--apply` flag**:
   - po-state.json `versions[].id` 전부 교체.
   - 동시에 ticket md frontmatter `version:` line 교체 (기존 line 형식 보존).
   - `<projectDir>/.productune/po-state.json.bak.<timestamp>` 백업 1회.
6. **idempotent**:
   - 이미 valid 한 id 는 skip (변경 0).
   - 재실행 시 dry-run 출력 = 변경 없음.

**CLI**:
```
node packages/gui/scripts/migrate-version-id.mjs --project-dir <path> [--apply]
```

#### E. UI rendering — version pill

**Path**:
- `packages/gui/src/components/workspace/SidePanelVersionList.tsx`
- `packages/gui/src/components/workspace/VersionHistoryView.tsx`
- `ProjectVersionsSection.tsx` (T-P4-086 사용)

**Rule**: version pill / label = `version.id` 그대로 렌더. project slug 합성 X.

```tsx
<VersionPill>{version.id}</VersionPill>   // "v1", "v0.1" — slug 안 붙음
```

cross-project 비교 영역 (HomeView recent projects 등) 에서는 project name 과 version 을 시각적으로 분리 표기:
```
[paepyeong] · v1   (X "paepyeong-v1")
```

- **migration 자동 실행** — 본 ticket 은 script 제공 + paepyeong 1회 apply 까지. CI 자동 migration X (사용자 confirm 후 apply).
- **legacy artificial id** (`legacy/phase3-fixes`) — T-P4-086 에서 도입한 표기 유지. 별 ticket 으로 정책 확장 검토.

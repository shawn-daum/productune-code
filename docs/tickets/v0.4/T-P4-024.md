## §2 Schema 정의

### §2.1 project-level — `<project>/.productune/git-rules.json` (tracked)

```jsonc
{
  "schema_version": 1,
  "useDevBranch": false,
  "useStagingEnv": false,
  "featureBranchPrefix": "feature/",
  "fixBranchPrefix": "fix/",
  "protectedBranches": ["main"],
  "autosaveTriggers": {
    "_locked": true,
    "_lockedReason": "Phase 5 lock",
    "events": ["ticket-status-change"]
  }
}
```

#### 필드 정의

| 필드 | 타입 | default | 사용자 편집 | source |
|---|---|---|---|---|
| `schema_version` | int | `1` | X | impl 자체. migration 시점에 사용 |
| `useDevBranch` | bool | `false` | O (토글) | R2 §4.4 dev branch 정책 |
| `useStagingEnv` | bool | `false` | O (토글) | R2 §4.5 Vercel staging mapping (Phase 5 동작) |
| `featureBranchPrefix` | string | `"feature/"` | O (text) | R2 §5.3 branch 명명 |
| `fixBranchPrefix` | string | `"fix/"` | O (text) | R2 §5.3 branch 명명 |
| `protectedBranches` | string[] | `["main"]` | X (display only) | `useDevBranch` 로 자동 계산 |
| `autosaveTriggers` | object | `{...}` | X (Phase 5 lock) | R2 §4.2 OQ-2 결정 |
| `autosaveTriggers._locked` | bool | `true` | X | GUI 의 read-only stamp |
| `autosaveTriggers._lockedReason` | string | `"Phase 5 lock"` | X | 사용자 hover tooltip |
| `autosaveTriggers.events` | string[] | `["ticket-status-change"]` | X | OQ-2 default. Phase 5 에서 unlock |

#### `protectedBranches` 자동 계산 규칙

```
useDevBranch === false → protectedBranches = ["main"]
useDevBranch === true  → protectedBranches = ["main", "dev"]
```

dev branch 의 명명 = 내부 hardcoded `"dev"` (OQ-T024-2 결정 영역, 본 plan §7
참조). 사용자에겐 "검증 환경" 으로만 노출 (R2 §4.4 dev branch 정책 정합).

저장 정책 — `protectedBranches` 는 git-rules.json 에 **derive 결과 저장**:
- 매 write 시 `useDevBranch` 기반으로 server (electron main) 가 재계산 → 파일에
  명시 저장. read 시점에 별도 derive 불요 (다른 ticket 의 single-source-of-truth
  유지).
- 사용자가 직접 jsonc 편집해서 mismatch 만든 경우 → next write 시 자동 정정 +
  status bar "protectedBranches 자동 정정됨" 1줄 안내 (§1.5.4 Feedback).

#### `autosaveTriggers.events` 의 R2 §4.2 OQ-2 정합

values:
- `"ticket-status-change"` — frontmatter `status` 변경
- (Phase 5) `"ticket-qa-status-change"` — `qa_status` 변경
- (Phase 5) `"ticket-qa-loops-increment"` — `qa_loops` 증분
- (Phase 5) `"turn-done"` — persona turn 종료

MVP 의 `["ticket-status-change"]` 는 사실상 OQ-2 결정의 `status` / `qa_status` /
`qa_loops` 3 trigger 를 한 토큰으로 묶음 — T-P4-021 spec 에서 detect 로직이 3
필드 모두 비교 (frontmatter previous vs current). 즉 schema 상 `"ticket-status-change"`
1 토큰은 "ticket frontmatter 의 상태 표상 필드 변경" 의 wrapper. Phase 5 에서
사용자 편집 unlock 시 3 필드를 개별 토큰으로 split.

### §2.2 global default — `~/.productune/git-rules.default.json`

동일 schema. 신규 project init 시 project-level 파일이 없으면 global default 를
copy 해서 project file 생성. global default 자체가 없으면 spec hard-coded default
(§2.1 의 default 컬럼) 로 자동 생성.

#### 첫 생성 시점

| 시점 | 처리 |
|---|---|
| `productune init` (T-P4-010) | global default 없으면 hard-coded default 로 생성. project-level git-rules.json 도 global default copy 로 생성 |
| GUI 새 project (T-P4-058 install 모달) | 위와 동일 — `bootstrapClaudeSettings` 후 `bootstrapGitRules` 추가 호출 |
| GUI 기존 project 열기 (`self-current`) | project-level 만 부재 시 — global default copy 또는 hard-coded default 로 생성. 사용자에게 silent (이미 init 통과) |
| GUI legacy migration (T-P4-058 `self-legacy`) | migration 의 `initProject` 호출 안에서 `bootstrapGitRules` 호출 |

#### global default 가 user 별로 다를 수 있는가

- O. 사용자가 자체적으로 `~/.productune/git-rules.default.json` 편집 시 — 본인의
  default 가 project 신규 생성 시 source. 신규 project 마다 동일 default 적용.
- 사용자 편집 UI = 본 ticket 영역 X. dev mode 에서 직접 파일 편집만 가능 (MVP).

### §2.3 schema validation

- json parse 실패 → fallback 으로 hard-coded default 사용 + status bar "git-rules.json
  파싱 실패. default 로 동작 중. [파일 열기]" inline error.
- 필드 누락 → 해당 필드만 default 로 보완. 사용자에게 silent (graceful merge).
- 필드 type mismatch (e.g. `useDevBranch` 가 string) → 해당 필드 default 로 교체
  + write back. status bar 알림 1줄.
- `_locked` 영역 사용자가 unlock 시도 → write 거부 + status bar "Phase 5 에서
  지원 예정. 편집 무시됨." 1줄.

### §2.4 atomic write

- tmp 파일 (`.git-rules.json.tmp`) 에 write → rename (atomic on POSIX).
- 실패 시 친절 에러 + [다시 시도] CTA — ticket md acceptance 항목 정합.

## §3 IPC 시그니처

T-P4-048 의 Settings 탭 renderer 가 호출하는 IPC. electron main 의 `git-rules`
namespace.

### §3.1 `git-rules:read`

```ts
// preload.ts
window.api.gitRules.read(projectDir: string): Promise<{
  project: GitRules;       // project-level (없으면 global 또는 hard-coded default)
  global: GitRules;        // global default (없으면 hard-coded default)
  merged: GitRules;        // 실제 동작 시 read source (project > global > hard-coded)
  source: 'project-file' | 'global-fallback' | 'hardcoded-default';
}>;
```

- `project` — `<projectDir>/.productune/git-rules.json` 파싱 결과 (또는 fallback).
- `global` — `~/.productune/git-rules.default.json` 파싱 결과 (또는 hard-coded).
- `merged` — 실제 사용. project 가 override (`{...global, ...project}`).
- `source` — UI 의 "현재 어디서 읽힘" 표시 (§4 Settings sub-tab note).

### §3.2 `git-rules:write`

```ts
window.api.gitRules.write(projectDir: string, partial: Partial<GitRules>): Promise<{
  ok: boolean;
  merged: GitRules;        // write 후 merged 상태
  error?: string;          // 실패 시 사용자 메시지 (한글)
}>;
```

- partial 만 받음 (전체 schema 아님). server 가 기존 file 과 merge → atomic write.
- `protectedBranches` 는 partial 에 포함되더라도 무시 — server 가 `useDevBranch`
  로 재계산해서 결과 stamp.
- `autosaveTriggers._locked === true` 인 필드 변경은 silent ignore (status bar
  알림 1줄).
- write 성공 시 다른 renderer 컴포넌트 (다음 ticket 발행 로직 등) 에 broadcast
  — `git-rules:changed` event 발송 (electron main → renderer 전체).

### §3.3 `git-rules:reset`

```ts
window.api.gitRules.reset(projectDir: string): Promise<{
  ok: boolean;
  merged: GitRules;        // reset 후 = global default 또는 hard-coded
  error?: string;
}>;
```

- project-level 파일 삭제 + global default 로 fallback. Settings UI 의 "기본값
  으로 되돌리기" CTA.
- confirm 모달 필요 (사용자 act 강제) — "현재 작업 흐름 규칙을 기본값으로
  되돌릴까요? 진행 중인 작업에는 영향이 없어요." [되돌리기] / [취소].

### §3.4 broadcast event — `git-rules:changed`

```ts
// preload.ts
window.api.gitRules.onChanged(callback: (merged: GitRules) => void): () => void;
// returns unsubscribe
```

- write / reset 직후 main 이 renderer 에 broadcast.
- 다음 ticket 발행 로직 (T-P4-020) 이 본 event subscribe — cache 무효화 hook.
- Settings UI 자체도 subscribe — 다른 창에서 동일 project 편집 시 즉시 sync
  (multi-window 정합).

### §4.3 인터랙션 정합

#### 토글 (useDevBranch / useStagingEnv)

- 클릭 즉시 IPC `write` 호출 → optimistic UI update.
- 성공 → "다음 작업부터 적용됩니다" status bar 1줄 (§1.5.4 Feedback).
- 실패 → 토글 revert + 친절 에러 toast + [다시 시도].
- `useDevBranch` 변경 시 `protectedBranches` display 가 즉시 재계산 visual update.

#### text input (featureBranchPrefix / fixBranchPrefix)

- onBlur 또는 Enter 시 IPC `write` 호출 (typing 중 매번 X — 부담 줄임).
- 빈 값 / 공백 only → validation 에러 inline (input 아래 1줄). save X.
- trailing `/` 자동 보완 — `"feature"` 입력 시 `"feature/"` 로 저장. UI 도 보완
  결과로 display.
- 특수문자 (`branch` 명 illegal char: 공백, `~`, `^`, `:`, `?`, `*`, `[`, `\`)
  → inline 에러 + save X.

#### display only (protectedBranches)

- read only. 사용자 클릭 X (선택조차 안 됨 — text 만).
- `useDevBranch` 토글 변경 시 즉시 list 업데이트.

#### locked area (autosaveTriggers)

## §5 Fallback 정책

### §5.1 우선순위

```
1. <project>/.productune/git-rules.json  ← 우선
2. ~/.productune/git-rules.default.json   ← 1 부재 시
3. spec hard-coded default                ← 둘 다 부재 시
```

### §5.2 자동 생성 시점

| 시나리오 | 1 (project) | 2 (global) | 3 (hardcoded) | 동작 |
|---|---|---|---|---|
| 신규 project init (T-P4-010) | X | X | use | global 생성 (hardcoded copy) + project 생성 (global copy) |
| 신규 project init | X | exists | - | project 생성 (global copy) |
| 기존 project 열기 (config.json 있음) | exists | exists | - | use project (정상 path) |
| 기존 project 열기 (config.json 있음) | X | exists | - | project 생성 (global copy) + use |
| 기존 project 열기 (config.json 있음) | X | X | use | global 생성 + project 생성 + use |
| legacy migration (T-P4-058) | X | exists | - | project 생성 (global copy) + use |

핵심 invariant — **첫 ticket 발행 시점 직전에 반드시 project-level 파일 존재**.
이는 T-P4-020 의 worktree 자동 생성이 schema read 에 의존하기 때문.

### §5.3 다른 user 잔재 (T-P4-058 hygiene 와 정합)

- `git-rules.json` 자체에는 absolute path / user-specific 내용 0 → cross-user
  transfer 시 hygiene 처리 불필요.
- 다른 user 의 `~/.productune/git-rules.default.json` 잔재 → 사용자 본인 user
  home 이므로 transfer 영향 X.
- 단 project-level 파일은 git tracked 이므로 PR / clone 으로 전파 — 의도된 동작
  (project 별 동일 rule 적용). 사용자 hygiene 우려 0.

### §5.4 git tracking 정책 (OQ-T024-1 영역)

- **project-level 파일** = git tracked (PRD spec). `.gitignore` 추가 X.
- 변경 시 자동 commit? — **OQ-T024-1 사용자 결정**. designer 잠정 권고: **자동
  commit X**. 사용자가 다음 ticket 발행 시점에 함께 commit (T-P4-021 의 autosave
  trigger 가 frontmatter 변경 시 캡처). 별 commit 발생 = git log noise.
- global default = user home → git tracked 자체 불가 (project repo 외).

```typescript
export interface GitRules {
  useDevBranch: boolean
  useStagingEnv: boolean
  featureBranchPrefix: string
  fixBranchPrefix: string
}

// 저장 대상: <projectDir>/.productune/git-rules.json
export function loadRules(projectDir: string): GitRules
export function saveRules(projectDir: string, rules: GitRules): void   // atomic tmp+rename
export function getDefault(): GitRules                                  // ~/.productune/git-rules.default.json r/w
export function getProtectedBranches(rules: GitRules): string[]        // derive only
```

**캐시 전략**: 모듈 레벨 `Map<string, GitRules>` — `saveRules` 호출 시 해당 key 제거.

```
  └── LockedRow: autosaveTriggers (Phase 5 lock chip)
```

**저장 흐름**:
1. 토글/텍스트 변경 → local state 업데이트
2. `saveRules` IPC 호출 (atomic)
3. 성공 → status bar toast "다음 작업부터 적용됩니다" 1.5s
4. 실패 → 인라인 에러 + [다시 시도] CTA

## 4. Settings 탭 통합 frame — LanguageSettings 흡수 방식

현재: `LeftSidebar.tsx` 의 `activeIcon === 'settings'` 분기 → `<LanguageSettings />` 직접 노출

변경 후:
```
LeftSidebar
  └── activeIcon === 'settings'
        └── SettingsView (새 컴포넌트)
              ├── sub-tab list: ["작업 흐름 규칙", "Language / 언어"]
              ├── activeSubTab === 'workflow' → WorkflowRulesPanel
              └── activeSubTab === 'language' → LanguageSettings (위치만 이동, 기능 동일)
```

`SettingsView.tsx` 위치: `packages/gui/src/components/workspace/SettingsView.tsx`

sub-tab 구조는 단순 state (string enum) — 추후 T-P4-048 통합 시 tab 배열에 push만 하면 확장됨.

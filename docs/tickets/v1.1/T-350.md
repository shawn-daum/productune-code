## Request

**UX 리포트 (shawn, 2026-07-14, 스크린샷)**: 첨부파일이 입력창(composer)에서는 예쁘게(칩) 나오는데, 전송된 채팅 버블에서는 "Attached files" 제목 + 경로 불릿이 메시지 상단에 raw markdown으로 렌더됨.

- 요구: 전송된 사용자 메시지 버블에서도 첨부를 **입력창과 같은 칩/필 형태**로, **버블 하단**에 표시. 본문 텍스트가 먼저, 첨부는 아래.
- 구조 참고: 첨부 경로는 PO(모델)에게 전달돼야 하므로 메시지 원문에는 남기되, 표시 레이어에서 변환하는 방식이 안전할 것 — 저장 포맷을 바꾼다면 기존 히스토리(이미 "Attached files" 블록이 박힌 메시지)도 렌더 시 동일하게 처리되어야 함.

## Acceptance

- A sent user message with attachments renders: body text first, attachment chips (filename, matching the composer's chip styling) at the bottom of the bubble — no raw "Attached files" heading/bullet markdown visible.
- Existing history messages containing the old "Attached files" block render the same way (render-time, no data migration).
- The PO still receives the attachment paths (model-facing content unchanged).
- Messages without attachments unaffected.

## Outcome

Render-time transform, no storage/model-facing format change:

- `packages/gui/src/lib/attachedFilesBlock.ts` (new) — `parseAttachedFilesBlock(text)` parses the leading `## Attached files` block (built by `useComposerAttachments.buildAttachedFilesBlock`, untouched) into `{ body, images, files }`, or returns `null` when the message has no such block. Regex is anchored so a real body that itself contains dash-prefixed lines is never swallowed into the attachment list (proven in tests, incl. adversarial cases).
- `packages/gui/src/components/workspace/chat/ImageChip.tsx` — `ImageChip`'s `onRemove` is now optional (omit → read-only, no X button); added sibling `FileChip` (same pill shape, file glyph, basename label, full path in `title` tooltip) for paperclip attachments. Both reused, unchanged, by the composer call sites.
- `packages/gui/src/components/workspace/chat/MessageBubble.tsx` — `UserBubble` calls `parseAttachedFilesBlock(message.text)`; when it matches, renders `parsed.body` via `MdRenderer` first (skipped entirely when empty — attachment-only sends), then a bottom `chipRow` of read-only `ImageChip`/`FileChip`. `message.text` itself is never mutated, so `chatAppendMessage`/`poSendMessage` payloads are unchanged — PO still receives the paths. When there's no block, falls through to the original single `MdRenderer` render (no-attachment messages unaffected). Applies identically to old history since it's the same on-disk text shape.

Verification (doctrine: proof of behavior, not just types):
- `attachedFilesBlock.test.ts` (7 cases) — image/file/mixed lines, empty-body attachment-only sends, no-block passthrough, and the adversarial "body contains dash-lines + blank line" case that would break a naive greedy regex.
- `MessageBubble.attachments.test.tsx` (3 cases, `renderToStaticMarkup` — same idiom as the existing `MdRenderer.href.test.tsx`) — asserts the real rendered DOM: no raw "Attached files" text, body index precedes chip index, path appears only inside `title="…"` (never as visible bullet text), attachment-only and no-attachment messages both render correctly.
- Full suite: `npx vitest run` → 28 files / 100 tests pass. `tsc --noEmit` clean on all touched files (one pre-existing, unrelated error in `SidePanelArtifacts.tsx` from the concurrent T-349 work-in-progress, not touched here).

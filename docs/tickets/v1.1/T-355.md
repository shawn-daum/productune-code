**버그 리포트 2건 (shawn, 2026-07-14, 스크린샷 — 같은 위임 상태 표면화 경로로 추정)**:

1. **상태바 사용량 표시 실종**: 하단 상태바에 원래 Claude Code 사용량이 떴는데, 지금은 그 자리에 "prdt-developer 위임 중…" 텍스트가 대신 표시됨. 사용량 표시가 밀려났는지/회귀인지 진단 필요. 부가 문제: **"prdt-developer"는 agent id 노출** — 사용자에겐 "Developer"(제품 역할명)로 보여야 함 (contracts의 persona naming 원칙).
2. **워커 스프라이트 비활성**: Developer가 백그라운드로 실제 작업 중인데 스프라이트가 활성(작업 중) 상태로 안 바뀜 — 위임 이벤트가 상태바에는 도달하는데 presence 스토어/스프라이트에는 반영이 안 되는 상태.

- 두 증상이 같은 위임 이벤트 파이프라인에서 갈라진 것인지 확인 — 상태바에는 오고 presence에는 안 오는 지점을 짚을 것.

## Acceptance

- Status bar shows the Claude Code usage display again (wherever it lived before); delegation status doesn't evict it (coexist or relocate — design judgment consistent with existing bar layout).
- Any user-visible delegation label uses the product role name ("Developer"), never the agent id ("prdt-developer").
- While a worker runs (background delegation included), its sprite activates in PersonaPresenceBar and deactivates on completion.
- Root cause identified for why the sprite path didn't fire while the status bar path did.

## Outcome

**Root cause (shared mechanism, bugs #1/#2)**: po-runner.ts's `handleToolUseHealth`
sends a generic, detail-less `'delegating'` health event the instant it sees a
`Task`/`Agent` tool_use, immediately followed (same tick) by a second
`'delegating'` event carrying the real `detail.persona` once `subagent_type` is
parsed off the same tool_use (po-runner.ts:1678/1696). Both events share the
same `HEALTH_PRIORITY` tier. The renderer's `sessionHealth.setHealth` only let a
`'delegating'` event through when it **advanced** past the current priority —
since state doesn't change between the two events, the second (real-persona)
one was silently rejected and the store kept the first's empty detail. That's
why the chip stuck on the ellipsis placeholder / a stale persona instead of the
worker's name, and why it visually "occupies" the status bar's left cluster
persistently. Confirmed via a failing→passing regression test
(`src/store/sessionHealth.test.ts`) that reproduced the exact two-event sequence
against the real store.

Layered on top, `detail.persona` — once it did land — was interpolated
**verbatim** (the raw dispatch agent id, e.g. `"prdt-developer"`) straight into
the user-facing label. Every other surface (ChatPanel's `verbForHealth`) already
maps agent id → product role via `personaIdFromAgentType` + `PERSONA_LABELS`;
`SessionHealthSegment` was the one path that never got that treatment.

**Fixes applied**:
1. `packages/gui/electron/po-runner.ts` — `emitHealth`: a detail-less
   `'delegating'` ping no longer blanks `ctx.lastDelegatedPersona` to `null`;
   it falls back to the previously-known persona (`?? ctx.lastDelegatedPersona`).
   Prevents a later, unrelated detail-less ping for the same still-running
   dispatch from re-passing the dedupe check and re-clobbering the renderer
   with a persona-less event. `emitHealth`/`makeHealthCtx` exported for testing.
2. `packages/gui/src/store/sessionHealth.ts` — `setHealth` now allows a
   same-priority `'delegating'` event through when it carries a persona the
   store doesn't already have (mirrors the runner's own persona-aware dedupe
   intent); a truly redundant repeat (same persona, or a detail-less repeat)
   is still a no-op.
3. `packages/gui/src/components/workspace/SessionHealthSegment.tsx` — new
   `personaLabel()` helper maps the raw agent id through
   `personaIdFromAgentType`/`PERSONA_LABELS` before interpolation (falls back to
   raw string only if unmapped, `'…'` if absent) — label now reads "Developer
   위임 중…", never "prdt-developer 위임 중…".
4. Layout coexistence (bug #1's remaining half — usage physically pushed
   off-screen): `SessionHealthSegment`'s wrapper was `flexShrink: 0`, same as
   `UsageBar`'s statusbar container. The segment used to be a rare, error-only
   chip when this layout was designed (T-PATCH-173); it's now common
   (thinking/delegating fire on nearly every turn), so two `flexShrink:0`
   siblings permanently compete for the StatusBar left cluster's width and
   whichever renders second gets pushed past the window edge — invisible, not
   removed. Changed the segment to `flexShrink: 1` + `minWidth: 0` (its label
   already has ellipsis/overflow-hidden) so it absorbs the squeeze and
   `UsageBar` (still `flexShrink: 0`) stays fully visible — coexistence per
   the acceptance's design-judgment allowance.

**Bug #3 (sprite) — investigation depth and confidence**: Extensively traced the
"does the delegating event reach presence" question. Built an integration-level
test harness (capturing `poEvents.ts`'s real `po:onHealth` handler against the
real `personaPresence`/`sessionHealth` stores, not mocks) and drove it through:
(a) the dual detail-less→real-persona event sequence, (b) a `'healthy'` parent-
turn-end while a worker is still `working` (T-PATCH-279's documented background
scenario), (c) a new user turn (`po:onMsgId`) starting while a worker is still
`working`. In every scenario tested, `usePersonaPresence`'s `entries.dev.state`
transitioned to `'working'` correctly and stayed there — the renderer's
presence-update branch (`poEvents.ts` `po:onHealth` handler) is unconditional on
`event.detail.persona` being a string, independent of whatever `sessionHealth`
did with the same event, so the dedupe bug above does not, by itself, explain a
presence-side miss.
The one concrete, reproducible gap fixed here (main-process fix #1 above) also
hardens presence indirectly: without it, a stray detail-less re-assert for a
persona whose real detail already fired earlier could silently reset the
runner's tracked persona to unknown, and a *subsequent* dispatch's own
detail-less pre-check would then race against a stale tracked value — the kind
of interleaving that would need live production stream-json logs (which
weren't available here) to nail with full certainty for the exact repro
shawn hit. Root cause is not fully closed to 100% confidence for the sprite
side specifically; if it reproduces again after this fix, capture the raw
`po:onHealth` event sequence (add a temporary `console.log` in
`poEvents.ts`'s handler, or inspect `.prdt/turns.jsonl`-adjacent session logs)
so the exact main-process envelope ordering can be inspected directly.

## Request

**UX 버그 리포트 (shawn, 2026-07-14, 스크린샷)**: claude 세션이 **rate limit**으로 죽었는데 GUI가 일반 오류로만 표시함.

- 관찰: 채팅에 "claude가 오류로 종료되었습니다 (코드 1). claude 가 예상치 못하게 종료됨 — 버전 확인 필요" / 하단 상태바에 "세션 오류 · 재시도"만 표시. 사용자 지적: "이거 지금 재시도 해도 될 리가 없잖아" — 리밋 상태에서 재시도 유도는 무의미.
- 기대:
  1. claude 종료 출력에서 rate-limit 신호를 감지 (stderr/stdout의 "hit your session limit · resets 1:10pm" 류 문구) → **rate limit임을 명시**하는 상태로 표시 (리셋 시각 포함: "사용량 한도 도달 — 1:10pm 리셋").
  2. 재시도 버튼: 리셋 전엔 비활성 또는 "리셋 후 재시도" 안내 (자동 재시도 예약까지는 설계 판단 — YAGNI 주의).
  3. 하단 패널의 사용량 표시가 100%를 반영하지 못한 점도 확인 — 리밋 상태와 사용량 게이지 연동 가능하면 함께.

## Acceptance

- When the claude process dies with a rate-limit message, the GUI surfaces a distinct rate-limit state (not the generic "버전 확인 필요" error), including the reset time parsed from the message when present.
- The retry affordance communicates that retry won't work until reset (disabled with countdown/notice, or equivalent — design judgment).
- Non-rate-limit exits keep the existing generic error behavior.
- Detection covered by unit tests against real captured message shapes.

## Outcome

done — root cause: claude reports a session/usage-limit hit via a stdout `type:'result', is_error:true` stream-json envelope (`result.error`, e.g. the captured "You've hit your session limit · resets 1:10pm (Asia/Seoul)"), not stderr. The pre-existing T-PATCH-271 exit-code classifier (`classifyExitError`/`extractRateLimitReset`, po-runner.ts) already covered "session limit" wording and was already unit-tested, but the `result` handler had its OWN narrower regex (`/rate_limit_error|429|rate.?limit/i`) that doesn't match "session limit"/"usage limit" phrasing — so this exact shape fell to `error-other`, producing the generic exit-error chat text + a health-smoke run that then (mis)reported "incompatible" (the observed "버전 확인 필요").

Fix:
1. `result` handler (po-runner.ts, `type === 'result'`) now reuses `classifyExitError`/`extractRateLimitReset` instead of its own regex, storing the classification on `HealthContext.resultErrorClassified` — the close handler consumes it (before falling back to stderr-tail classification) so BOTH sources (stdout JSON result and stderr) land on identical health state + ko chat copy, and the code===0 "recover to healthy" path no longer clobbers a rate-limited state back to healthy when a limit was reported but the CLI still exited cleanly.
2. `extractRateLimitReset` gained a 4th priority: a human clock-time shape ("1:10pm (Asia/Seoul)", no "at", no ISO) — captured as display-only text (timezone kept verbatim, no epoch conversion attempted, per dispatch instruction). Also fixed a latent bug in the existing ISO "resets at …" regex: its character class silently truncated a human time like "3:45pm" down to "3:45" (dropping the am/pm marker) when the CLI phrasing happened to include "at" — now gated to only accept the match when it actually looks like ISO (has a 'T' or a YYYY-MM-DD date prefix).
3. Extracted `buildResetHint` (shared by both classification sources) to remove triplicated reset-phrase formatting.
4. RateLimitBanner (chat/RateLimitBanner.tsx) now has 3 modes instead of 2: `exact` (retryAfterSec or parseable ISO resetAt — ticks down to a real deadline, unchanged), `estimate` (neither present — 60s guess ticking down, unchanged), and new `static` (resetAt present but NOT epoch-parseable — a human clock time) which shows the raw time text with NO fake ticking countdown (a countdown against a made-up deadline would be misleading) and does not fire `onExpired` — the composer/send stays disabled via the existing `rateLimited` health-state gate in ChatPanel until the user manually retries. New locale key `workspace.chat.rateLimit.limitReached` (en+ko) renders that static message.
5. Non-rate-limit exits unchanged (auth/unclassified paths untouched; only the usage/rate-limit branch of the `result` handler was rewired).

Retry affordance: already disabled during `rate-limited` health state pre-existing (ChatPanel `disabled={!project || rateLimited}` on composer + both send buttons) — no change needed there, just ensuring the state correctly becomes `rate-limited` instead of `error-other` for this message shape.

Tests: new `electron/po-runner.ratelimit.test.ts` (case-list + vitest driver, matching repo convention) — 3 vitest cases / 19 sub-cases covering `classifyExitError`, `extractRateLimitReset`, `buildResetHint` against the real captured message, wording variants, the pre-existing ISO shape (regression), and messages with no parsable reset time. `npx vitest run` → 103/103 pass (repo-wide, no regressions). `tsc --noEmit` clean. `npm run build` (tsc + vite build, main+preload) green. `npm run lint` (locale key parity + protected tokens) clean.

Not done / left for the PO: no live/CUA reproduction of an actual claude session-limit exit was run (matches T-PATCH-271's own outcome note that live cap/auth exit messages are a CUA-flagged gap) — this fix closes the classification gap found by code inspection + the literal captured message text from the ticket, verified via unit tests only.

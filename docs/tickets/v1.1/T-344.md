## Request

**버그 리포트 (shawn, 2026-07-14)**: 한글 IME 조합 중 전송 시 조합 글자가 인풋에 잔류.

- 재현: "확정" 입력 → 마지막 글자 "정"이 아직 조합 중(커서 깜박)일 때 **Cmd+Enter** → 메시지는 "확정"으로 정상 전송되는데, 인풋창에 "정"이 남음.
- 원인 유형: composition(조합) 이벤트 미처리 — 전송 시 조합 중인 텍스트를 flush/취소하지 않고 입력값만 비워서, IME가 조합 세션을 이어가며 글자를 재삽입하는 전형적 패턴.
- 범위: ChatPanel composer + FreshComposer 등 텍스트 전송 입력 전반 — 동일 핸들러면 같은 버그.

## Acceptance

- Typing Korean text and pressing Cmd+Enter mid-composition sends the full text and leaves the input completely empty (no residual composing character).
- Behavior verified for both the running-turn queue path and the idle send path, and on FreshComposer if it shares the pattern.
- No regression for non-IME (English) input or plain Enter/newline behavior.

## Outcome

**원인**: `ChatPanel.tsx`와 `FreshComposer.tsx` 둘 다 동일 패턴(T-PATCH-264) — Cmd+Enter 키다운 핸들러가 조합 완료된 텍스트를 정상적으로 읽어 전송은 잘 되지만(그래서 "확정" 자체는 온전히 나감), `setDraft('')`는 React의 controlled `value`만 비울 뿐 텍스트필드 DOM 노드에 붙어있는 브라우저 네이티브 IME 조합(composition) 버퍼는 건드리지 못함. 이 버퍼는 controlled value로 접근 불가능한 별도 오버레이라, 컴포지션 세션이 살아있는 채로 값만 비우면 IME가 잠시 후 조합 중이던 글자("정")를 다시 흘려넣음 — 그래서 방금 비운 인풋에 마지막 글자만 잔류.

**수정**: 두 컴포넌트 모두 전송 후 `<textarea>`에 `key={composerKey}`를 걸고 클리어 시점마다 `composerKey`를 bump — DOM 노드를 통째로 리마운트시켜 조합 세션 자체를 버림(조합을 취소하는 JS API가 없어, 크로스브라우저로 확실한 방법은 이것뿐). 전송 경로 3곳 모두 커버:
- ChatPanel 큐잉 경로 (스트리밍 중 enqueue)
- ChatPanel idle 전송 경로
- FreshComposer 최초 전송 경로 (동일 패턴 확인, `autoFocus`가 있어 리마운트 시 포커스는 자동 복구)

ChatPanel은 `autoFocus`가 없어 리마운트로 포커스가 빠지므로, `composerKey` 변경을 감지해 `taRef.current?.focus()`로 복구하는 effect를 별도로 추가(첫 렌더는 가드로 스킵). 비-IME(영문) 입력이나 일반 Enter/줄바꿈 경로는 건드리지 않음 — 리마운트는 전송 성공 후에만 발생하므로 회귀 없음.

**DoD**: `tsc --noEmit` clean · `vitest run` 21 files / 64 tests green (변경 전과 동일 — 이 변경은 순수 UI 글루라 새 단위 테스트 대상 로직 없음, RTL/jsdom 인프라 부재는 T-343과 동일 사유). 실제 한글 IME 조합 중 Cmd+Enter 재현은 브라우저 네이티브 컴포지션 이벤트가 필요해 vitest(jsdom 미탑재, environment: node) 환경에서 재현 불가 — 코드 경로는 리마운트가 확실히 조합 세션을 파괴함을 보장하는 표준 패턴이라 판단, 실제 한글 입력 재현 확인은 QA 라이브 검증에 넘김.

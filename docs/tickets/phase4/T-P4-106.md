# T-P4-106 — `productune init` 시 user-global doctrine idempotent 설치

## §1 Background

### 1.1 발단 — paepyeong PO 사고

v0.4-meta-dogfood dogfood 중 paepyeong 프로젝트에서 PO 실행 시 `~/.productune/po-instructions.md` 부재로 doctrine 강제 실패 발생. 원인: 해당 사용자가 `install.sh` 를 한 번도 실행하지 않고 `productune init` 만 반복 실행한 상태.

사용자 directive verbatim:
> "그것도 init에 포함해주면안돼?"

`install.sh` L602–630 이 doctrine setup 의 SoT 이지만, 사용자 mental model 에서 **"productune init = 작업 준비 완료"** 이므로 doctrine 설치도 init 경로에서 보장해야 한다.

### 1.2 현재 구조

| 경로 | 역할 |
|---|---|
| `packages/core/scripts/install.sh` L602–630 | user-global doctrine 설치 (SoT 역할, 수동 1회 실행) |
| `packages/core/src/init.ts` `initProject()` | project-local scaffold. `bootstrapPersonaMemory` + `bootstrapClaudeSettings` 만 호출. user-global `~/.productune/` 미건드림 |
| `packages/core/po/` | `po-instructions.md`, `po-memory.md.template`, `sections/*.md` 소스 |

`install.sh` 를 실행하지 않은 환경에서 `productune init` 만 실행 → `~/.productune/po-instructions.md` 미생성 → PO doctrine 실패.

### 1.3 결정 사항 (OQ 해소)

| OQ | 결정 | 근거 |
|---|---|---|
| **OQ-T106-1** po-instructions.md SoT | **npm package bundle** (`po/` 를 `package.json files[]` 에 포함) | publish snapshot 정확성 보장. monorepo working tree 에 runtime 의존 없음. |
| **OQ-T106-2** init trigger | **`productune init <slug>` 통합** (별도 서브커맨드 없음) | 사용자 mental model 단순화. "init = 작업 준비 완료" 일관성. |
| **OQ-T106-3** 변경 감지 방식 | **SHA-256 hash compare** (`crypto.createHash('sha256')`) | 간단하고 deterministic. version frontmatter 파싱 불필요. |

## §2 Scope

### A. `@productune/core` package — `po/` bundle 포함

**`packages/core/package.json`** — `files` 필드 추가:

```json
{
  "files": ["dist", "po"]
}
```

현재 `package.json` 에 `files` 필드 없음(private: true). 내부 monorepo 패키지이므로 npm publish 는 미사용이나, runtime 에서 package root 기준 `po/` 경로 resolve 를 보장하기 위해 명시. tsc build 는 TS→JS 만 처리하므로 `po/` (text 파일) 는 build copy 단계 불필요 — source 위치(`packages/core/po/`) 를 그대로 사용.

**runtime path resolve** — `init.ts` 내부에서:

```ts
import { fileURLToPath } from 'url'

// dist/init.js 기준 → ../../po (packages/core/po/)
const DOCTRINE_SRC = fileURLToPath(new URL('../../po', import.meta.url))
```

> `import.meta.url` — ESM (`"type":"module"`) 환경. `__dirname` 대체. tsc target 에 무관하게 동작.

---

### B. `init.ts` — `bootstrapUserGlobalDoctrine()` 신규 함수

**`packages/core/src/init.ts`** 에 새 export 함수 추가:

```ts
export function bootstrapUserGlobalDoctrine(): void
```

내부 동작 (순서):

#### B.1 디렉터리 보장

```ts
const PRODUCTUNE_HOME = path.join(os.homedir(), '.productune')
const SECTIONS_HOME   = path.join(PRODUCTUNE_HOME, 'sections')

fs.mkdirSync(PRODUCTUNE_HOME, { recursive: true })
fs.mkdirSync(SECTIONS_HOME,   { recursive: true })
```

#### B.2 `po-instructions.md` — hash compare + backup + update

```
src : DOCTRINE_SRC/po-instructions.md
dest: ~/.productune/po-instructions.md
```

- dest 없음 → copy. trace: "[init] 시스템 파일 설치 완료".
- dest 있음 + hash 동일 → skip (no trace).
- dest 있음 + hash 다름 → `.bak.<ts>` backup 후 copy. trace: "[init] 시스템 파일을 최신 버전으로 업데이트했습니다." (사용자 노출 — 자연어).

hash helper (내부):

```ts
function sha256(filePath: string): string {
  return crypto.createHash('sha256')
    .update(fs.readFileSync(filePath))
    .digest('hex')
}
```

`import crypto from 'crypto'` — Node.js built-in. 신규 dep 없음.

#### B.3 `po-memory.md` — seed only (절대 overwrite 금지)

```
src : DOCTRINE_SRC/po-memory.md.template
dest: ~/.productune/po-memory.md
```

- dest 없음 → copy (template → po-memory.md).
- dest 있음 → **완전 skip**. 사용자 long-term memory 보존. 이유 trace 없음.

#### B.4 `sections/*.md` — 파일별 hash compare + backup + update

```
src : DOCTRINE_SRC/sections/*.md  (glob)
dest: ~/.productune/sections/<basename>.md
```

각 파일:
- dest 없음 → copy.
- dest 있음 + hash 동일 → skip.
- dest 있음 + hash 다름 → `.bak.<ts>` backup 후 copy.

> install.sh 는 sections 전체를 rm 후 재copy (wipe). init.ts 는 file-by-file 방식 — 더 보수적이고 안전 (orphan 파일 잔류 허용). orphan 정리는 별 ticket (install.sh deprecation 범위).

#### B.5 `productune.env` — seed only

```
dest: ~/.productune/productune.env
```

- dest 없음 → seed:

```
engine=claude
```

- dest 있음 → skip. engine 선택 / REPO_PATH 등 사용자 커스텀 보존.

> `install.sh` 는 interactive engine picker 포함 (L650+). init.ts 는 non-interactive → `engine=claude` default. install.sh 실행 시 덮어씌워지는 구조이므로 충돌 없음.

#### B.6 stderr trace

init 완료 시 1회 출력:

```
[init] 시스템 파일 설치 완료
```

> "worktree" / "sections" 등 내부 어휘 노출 없음. 자연어.

업데이트 발생 시 (B.2 hash 불일치):

```
[init] 시스템 파일을 최신 버전으로 업데이트했습니다. (기존 파일 .bak 백업됨)
```

모두 skip 된 경우(idempotent 재실행): **trace 없음** (조용한 재실행).

### C. `initProject()` — `bootstrapUserGlobalDoctrine` 호출 추가

```ts
export function initProject(opts: InitOptions): ProjectConfig {
  // ...기존 로직...
  bootstrapPersonaMemory(opts.projectDir)
  bootstrapClaudeSettings(opts.projectDir)
  bootstrapUserGlobalDoctrine()   // ← 신규 호출
  return config
}
```

호출 위치: `bootstrapClaudeSettings` 이후. 순서 무관(독립 함수)하나 project scaffold 완성 후 global 보장 순서가 자연스러움.

---

### D. `install.sh` 와 정합

install.sh **변경 없음**. 이유:

1. `bootstrapUserGlobalDoctrine` 는 idempotent → install.sh 와 init.ts 양쪽에서 doctrine 처리해도 중복 무해.
2. install.sh 는 agents symlinks, codex config, engine picker(interactive) 등 init.ts 범위 밖 작업을 포함 → 완전 대체 불가.
3. install.sh 완전 deprecation = 별 ticket (사용자 지정, Out of scope).

**SoT 정책**: doctrine 파일 원본 = `packages/core/po/`. init.ts 와 install.sh 양쪽 모두 이 디렉터리를 source 로 사용 (현재도 동일).

---

### E. `--skip-doctrine` 플래그 (Escape path)

`InitOptions` 에 optional flag 추가:

```ts
export interface InitOptions {
  slug: string
  projectDir: string
  initialVersionId?: string
  skipDoctrine?: boolean   // ← 신규
}
```

`initProject` 내부:

```ts
if (!opts.skipDoctrine) bootstrapUserGlobalDoctrine()
```

CLI entry point (`packages/core/src/cli.ts` 또는 해당 entry) 에서 `--skip-doctrine` arg 파싱 → `skipDoctrine: true` 전달. DS §1.5.5 Escape 준수.

> `--skip-doctrine` flag 의 CLI 파싱 위치는 developer 판단 (init CLI handler 소재 파일). Implementation note.

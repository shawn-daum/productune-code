# T-P4-101: Fresh project entry — ChatGPT/Lovable식 “아이디어 먼저” 1-input 화면

> GUI 에서 새 프로젝트를 만들거나, non-productune 폴더를 열어 init/install 을 막 끝낸 직후에는 지금처럼 ActivityBar / Sidebar / MainPanel / PO Chat 전체를 한 번에 보여주지 않는다. **persisted onboarding state** 가 `pending` 인 프로젝트는 중앙 1-input composer 만 먼저 보여주고, 사용자의 **첫 real message 가 실제 send/start kick-off 에 성공한 순간** onboarding 을 `done` 으로 뒤집고 normal workspace 전체 UI 를 reveal 한다.

## §1 Background

### 1.1 사용자 요청 verbatim (2026-05-12)

> Gui project onboarding gui으로 프로젝트 생성하거나 init했을때, 모든 UI를 다 보여주지말고 pochat에 default로 ‘만들고 싶은 제품 아이디어를 얘기해주세요. Idea를 PO와 인터뷰해서 PRD작성을 먼저 시작합니다.’ 대충 이런 내용으로 넣어줘. Chatgpt / lovable 초기 input 화면 처럼 딱 입력창 하나만 넣어주고. 이거 입력하고나면 우리 전체 ui를 보여줘.

### 1.2 현재 상태

신규 프로젝트 진입 경로는 모두 곧바로 full workspace 로 들어간다.

- `project:create` 성공 → `App.tsx` 가 즉시 `WorkspaceShell` mount
- `project:installAt` 성공 → 동일하게 즉시 `WorkspaceShell` mount
- `WorkspaceShell` mount 직후:
  - ActivityBar / LeftSidebar / Breadcrumb / MainPanel / StatusBar / ChatPanel 전부 노출
  - Tickets board tab auto-open
  - ChatPanel 은 empty hint (`Start a conversation with PO.`) 만 보임

즉, 사용자가 **아직 제품 아이디어 1문장도 입력하지 않았는데** 정보 밀도 높은 운영 화면을 먼저 본다. 이건 사용자의 현재 mental model (“아이디어 말하기 → PO 인터뷰 → PRD 시작”) 과 순서가 반대다.

### 1.3 기존 fresh 판정 접근의 한계

초기 구상은 매 mount 마다 아래를 다시 읽어 `fresh project` 여부를 재계산하는 방식이었다.

- `chat.json.messages.length === 0`
- `po-state` 의 `current_task`, `phase_history`, `recent_turns` 흔적 부재

이 방식은 fallback 으로는 쓸 수 있지만, **primary contract** 로 두기에는 문제가 있다.

- onboarding 여부가 명시적 상태가 아니라 여러 파일의 “깨끗함” 추론에 의존함
- mount 시점마다 판정 로직이 늘어나고 hydration gating 이 복잡해짐
- chat/session 정리, state migration, partial failure 상황에서 의도가 흔들릴 수 있음
- “새 프로젝트 첫 진입” 과 “대화가 우연히 비어 있는 기존 프로젝트” 를 구분하는 모델이 약함

### 1.4 문제 정의

초기 진입에서 필요한 행동은 사실 1개뿐이다.

> **“무엇을 만들고 싶은지 말하기”**

그리고 이 1-step UX 는 **명시적으로 persisted 된 onboarding state** 로 제어되어야 한다.

- 새 프로젝트 첫인상에서 부담을 줄여야 함
- PRD-first flow 가 workspace chrome 보다 먼저 와야 함
- 첫 입력 완료 판정은 “실제 첫 user send 가 시작되었는가” 로 봐야 함
- send 실패 시 onboarding 을 끝낸 것으로 오판하면 안 됨
- legacy 프로젝트에 대한 fallback 은 가능하되, 주된 설계가 되어선 안 됨

## §2 목표 / 비목표

### 2.1 목표

1. fresh onboarding 여부를 **명시적 persisted state** 로 관리한다.
2. 이 state 는 **딱 두 시점** 에서만 `pending` 으로 기록된다.
3. workspace entry 시 persisted onboarding state 가 `pending` 이면 **minimal idea-entry screen** 을 먼저 보여준다.
4. 첫 real user message 가 **성공적으로 send/start kick-off** 된 순간 onboarding state 를 `done` 으로 뒤집고 full workspace 를 reveal 한다.
5. 첫 send 실패 시 onboarding state 는 유지되고 draft 는 보존된다.

### 2.2 비목표

- full workspace 구조 자체 재설계
- PO 응답 품질/프롬프트 변경
- Tickets board / Main pane 기본 탭 정책 재설계
- onboarding wizard (`productune.env`, language, engine, wiki) 흐름 변경
- legacy 프로젝트 전체를 신규 onboarding 체계로 일괄 migration 하는 작업

## §3 결정 요약

### A. fresh/onboarding 판정의 primary source 는 **persisted onboarding state** 다

workspace entry 시 우선 확인하는 것은 `chat.json`/`po-state` cleanliness 추론이 아니라, 프로젝트에 저장된 explicit onboarding state 다.

권장 의미 모델:

- `onboarding.status = 'pending' | 'done'`
- optional metadata: `source = 'gui-create' | 'install-at' | 'legacy-fallback'`, `updated_at`

핵심은 **상태 이름과 전이 규칙이 명시적** 이어야 한다는 점이다. 정확한 저장 위치/필드명은 implementation 에 맞춰 정하되, 프로젝트 단위 persisted state 여야 한다.

### B. `pending` 기록은 오직 두 순간에만 한다

다음 성공 시점에만 onboarding 을 `pending` 으로 쓴다.

1. GUI 새 프로젝트 생성 성공 직후
2. non-productune 프로젝트를 열고 init/install 성공 완료 직후

즉, 매 mount 시 “혹시 fresh 인가?”를 다시 계산해서 `pending` 을 만들지 않는다.

### C. workspace entry 는 persisted onboarding state 를 먼저 본다

- `onboarding.status === 'pending'` → idea-entry screen
- `onboarding.status === 'done'` → full workspace
- onboarding field 없음 → **secondary / minimal legacy fallback** 만 수행

### D. onboarding 완료 판정은 **첫 real user send kick-off 성공** 이다

완료 시점은 assistant 응답 완료가 아니다.

다음이 성공적으로 이어진 순간 onboarding 을 `done` 으로 바꾼다.

1. 사용자의 첫 real input submit
2. user message append/persist 성공
3. `po:sendMessage` / send-start handshake 성공
4. onboarding `pending → done`
5. full workspace reveal

즉, “첫 메시지를 실제로 보냈다” 가 completion 기준이다.

### E. 첫 send 실패 시 onboarding 은 유지된다

- send/start 실패
- onboarding status 는 그대로 `pending`
- user draft 보존
- minimal screen 유지
- inline error / retry 제공

### F. intro copy 는 **UI text** 이지 synthetic chat message 가 아니다

이 문구를 `chat.json` 에 assistant bubble 로 저장하지 않는다.

- fresh entry hero copy = non-persisted UI text
- 첫 real chat history 는 사용자의 첫 입력부터 시작
- session replay 시 가짜 assistant 첫 메시지가 생기지 않음

## §4 State model

### 4.1 Entry states

| 상태 | 조건 | 보여줄 화면 |
|---|---|---|
| `loading-entry` | onboarding state resolve 전 | neutral dark shell only (flash 방지) |
| `idea-entry` | persisted onboarding status = `pending` | centered idea-first screen |
| `full-workspace` | persisted onboarding status = `done` | 기존 `WorkspaceShell` full UI |
| `legacy-fallback` | onboarding field 없음 | 보수적 fallback 판정 후 `idea-entry` 또는 `full-workspace` |

### 4.2 Persisted onboarding contract

최소 계약은 아래와 같다.

- 프로젝트 단위 persisted 값이어야 한다.
- 앱 재실행 / reopen 후에도 유지되어야 한다.
- `pending` 은 init success 계열 시점에서만 기록된다.
- `done` 은 첫 real send-start success 에서만 기록된다.
- 일반 mount/hydration 에서는 이 값을 재계산해 덮어쓰지 않는다.

### 4.3 Legacy fallback 원칙

onboarding field 가 없는 legacy 프로젝트만 예외적으로 최소 fallback 을 사용한다.

권장 원칙:

- 명백히 fresh 라는 강한 신호가 있을 때만 `idea-entry`
- 조금이라도 기존 작업 흔적이 있으면 `full-workspace`
- fallback 결과를 primary UX contract 처럼 복잡하게 키우지 않음

즉, fallback 은 “옛 프로젝트 호환용 안전장치”이지, 정상 flow 의 핵심 로직이 아니다.

## §5 Desired UX flow

### 5.1 Trigger scope

적용 대상:

1. GUI `새 프로젝트 만들기` 성공 직후
2. `기존 폴더 열기` 로 non-productune project 를 열고 `init/install` 성공 직후
3. app relaunch / Cmd+R / `lastProject` restore 이후에도 onboarding status 가 아직 `pending` 인 프로젝트

비적용 대상:

1. onboarding status 가 `done` 인 프로젝트
2. legacy fallback 상 기존 작업 흔적이 있어 `full-workspace` 로 판정된 프로젝트
3. 이미 첫 real send 를 시작한 프로젝트

### 5.2 Minimal screen spec

#### Hero copy

기본 한국어 문구:

- headline: `만들고 싶은 제품 아이디어를 얘기해주세요.`
- supporting copy: `Idea를 PO와 인터뷰해서 PRD 작성을 먼저 시작합니다.`

영문 키도 동등 제공:

- headline: `Tell us the product idea you want to build.`
- supporting copy: `PO will interview the idea first and start by drafting the PRD.`

> `PO`, `PRD` literal 은 양 locale 에서 그대로 유지 가능.

#### Composer

- 화면 중앙 고정, max-width 680~760px 범위
- dark surface 위 1개 입력창만 강조
- textarea 1개 + send CTA 1개
- autofocus
- IME composition-safe (`isComposing` 중 Enter submit 금지)
- 파일 첨부 버튼, persona selector, quick prompts, recent list **없음**

#### Visual tone

- ChatGPT/Lovable 류의 “빈 캔버스 + 첫 질문 하나” 패턴
- 과한 logo/카드/설명 목록 없음
- 우리 current dark theme 토큰 유지
- 입력창은 현재 ChatPanel textarea 스타일을 재사용하거나 거의 동일 톤으로 맞춘다

### 5.3 First-send transition

첫 submit 시 이상적인 순서:

1. 사용자가 idea-entry 에 첫 real text 입력
2. submit 수행
3. user message persist 성공
4. send/start kick-off 성공
5. onboarding status `pending → done` persisted
6. `idea-entry` 종료
7. 기존 workspace grid reveal
8. 오른쪽 PO Chat 에 방금 보낸 첫 user message + 이어지는 stream 표시

중요 포인트:

- reveal 은 assistant 답변 완료를 기다리지 않는다
- reveal 은 “보내기 성공적으로 시작됨” 이후에 일어난다
- onboarding done 전환은 send 실패 이전에 성급히 일어나면 안 된다

### 5.4 Failure path

첫 입력 전송 실패 시:

- onboarding status 는 `pending` 유지
- full workspace reveal X
- draft 텍스트 보존
- inline 1-line error 또는 retry affordance 제공
- 사용자가 재시도 후 send/start 성공하면 그때 `done` 전환 + reveal

### 5.5 Exit rule (one-way)

한 번 `done` 이 된 project 는 다시 `idea-entry` 로 돌아가지 않는다.

- app 재실행 후에도 `done` 이면 full workspace 유지
- chat/session 정리 등 개별 파일 상태만으로 onboarding 을 다시 열지 않는다
- onboarding 재오픈은 명시적 reset 기능이 따로 생기기 전까지 지원 대상 아님

## §6 UX expectations / behavior details

### 6.1 Hydration flash 금지

onboarding state resolve 전 full grid 를 먼저 그리면 “전체 UI가 잠깐 보였다가 사라지는” flash 가 생긴다.

따라서 다음 원칙 필요:

- onboarding persisted state resolve 전 full grid 렌더 X
- Tickets board auto-open side effect 도 `full-workspace` 모드에서만 실행
- 판정 전 임시 상태는 blank dark shell 또는 아주 약한 skeleton 정도로 제한
- legacy fallback 도 onboarding field 부재가 확인된 뒤에만 최소 범위로 수행

### 6.2 Post-reveal workspace 는 기존 동작 최대한 유지

이 ticket 의 핵심은 **entry simplification + explicit onboarding contract** 이다. 첫 입력 후 보이는 전체 UI 는 기존 동작을 최대한 그대로 둔다.

- 기존 grid layout 유지
- 기존 ChatPanel stream pipeline 유지
- 기존 status / sidebar / tabs 유지
- main pane default tab 정책은 현행 유지 가능

### 6.3 Accessibility / input expectations

- keyboard-only send 가능
- focus 초기 진입 시 textarea 에 위치
- placeholder/example 문구는 보조 정보일 뿐, 실제 hero copy 보다 시각 우선순위 낮게
- 한국어 IME 조합 중 Enter 오동작 금지

## §7 Acceptance

- [ ] GUI 새 프로젝트 생성 성공 직후, 프로젝트 onboarding state 가 persisted `pending` 으로 기록된다.
- [ ] non-productune 폴더를 열어 init/install 성공 완료 직후도 동일하게 onboarding state 가 persisted `pending` 으로 기록된다.
- [ ] workspace entry 의 primary 판정은 `chat.json` / `po-state` cleanliness 재계산이 아니라 persisted onboarding state 다.
- [ ] `onboarding.status = pending` 인 프로젝트는 ActivityBar / Sidebar / MainPanel / StatusBar / ChatPanel 대신 **중앙 idea-entry screen** 을 먼저 본다.
- [ ] onboarding state 가 `done` 인 프로젝트는 기존 full workspace 로 바로 진입한다.
- [ ] onboarding field 가 없는 legacy 프로젝트만 secondary fallback 을 사용한다.
- [ ] legacy fallback 은 보수적으로 동작하며, 기존 작업 흔적이 조금이라도 있으면 full workspace 를 우선한다.
- [ ] 첫 입력 전에는 Tickets board auto-open 이 실행되지 않는다.
- [ ] 첫 real user input 이 user message persist + send/start kick-off 에 성공하면, 같은 프로젝트 맥락에서 onboarding state 가 `done` 으로 persisted 되고 full workspace 가 reveal 된다.
- [ ] assistant 첫 응답이 끝날 때까지 기다리지 않고, 첫 turn 시작 시점에 reveal 된다.
- [ ] 첫 입력 send/start 실패 시에는 onboarding state 가 `pending` 으로 남고, idea-entry screen 유지 + draft 보존 + 재시도 가능.
- [ ] hero 문구는 UI text 로만 보이며 `chat.json` 에 synthetic assistant message 로 저장되지 않는다.
- [ ] app relaunch / Cmd+R 후에도 onboarding state 가 `pending` 이면 idea-entry 유지, `done` 이면 full workspace 유지.
- [ ] 한국어 IME 조합 중 Enter submit 오동작이 없다.
- [ ] hydration 중 full UI flash 가 없다.

## §8 Edge cases

1. **project created successfully, but app reopened before first send**  
   onboarding state 가 이미 `pending` 으로 persisted 되어 있으므로, 다시 열어도 idea-entry 가 보여야 한다.

2. **first send failure after draft entered**  
   IPC/CLI 오류로 `po:sendMessage` 또는 send-start handshake 가 실패하면 onboarding 은 끝나지 않는다. `pending` 유지, draft 보존, retry 가능해야 한다.

3. **user message persisted but send start failed**  
   completion 기준은 “첫 real send 가 실제로 시작됨” 이다. 따라서 partial success 만으로 `done` 으로 넘기지 않는다. 필요 시 idempotent retry 가 가능해야 한다.

4. **legacy project without onboarding field**  
   onboarding flag 가 없으면 secondary fallback 을 수행할 수 있다. 단, 빈 chat 만 보고 적극적으로 onboarding 으로 보내기보다, 기존 작업 흔적이 조금이라도 있으면 full workspace 우선이 안전하다.

5. **existing project with manually cleared chat**  
   chat 이 비어 있어도 onboarding state 가 이미 `done` 이면 idea-entry 로 돌아가지 않는다.

6. **non-productune project open before install completes**  
   onboarding `pending` 기록 시점은 open 시점이 아니라 init/install 성공 완료 시점이다. 실패/중단 상태에서는 onboarding contract 를 섣불리 쓰지 않는다.

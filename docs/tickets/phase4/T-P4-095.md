# T-P4-095: Version id naming convention — project slug prefix 금지

> version id 표기 `^v\d+(\.\d+)?$` 단일 규칙. paepyeong-v1 같은 slug prefix 형식 거부 + legacy migration.

## §1 Request

사용자 2026-05-12 dogfood feedback: "버전 naming 도 규칙 필요하겠다. paepyeong-v1 X, v1 O."

현 paepyeong project 의 `po-state.json` 에 `versions[0].id = "paepyeong-v1"` 박혀 있음 — project slug 가 version 앞에 중복 prefix. git tag / SemVer 친숙 패턴과 어긋나고, 사용자 GUI 상에서 본인 project slug 가 version pill 안에 다시 노출되는 어색함.

→ version id 표기 룰 정합 (`v1` / `v0.1` 만) + paepyeong 등 legacy migration + onboarding / PO flow / ticket lint / UI rendering 전 영역 enforce.

## §2 Inputs

- PRD §10 versioning anchor — `docs/prd/productune.md`
- Design plan (본 ticket 자매): `docs/design/T-P4-095/plan.md`
- Precedent: `docs/tickets/phase4/T-P4-086.md` (ticket↔version frontmatter migration — script + bulk apply 패턴 재사용)
- Doctrine: `~/.productune/sections/lifecycle.md` (Version transition spec)
- Existing script reference: `packages/gui/scripts/migrate-ticket-version.mjs`

## §3 Naming rule (spec)

- version id MUST match `^v\d+(\.\d+)?$`
- 허용 예: `v1`, `v2`, `v0.1`, `v0.2`, `v1.2`
- 금지 예: `paepyeong-v1` (slug prefix), `v1-rc` (pre-release), `version-1`, `V1`, `1.0`

자세한 rationale + §1.5 self-check 는 plan §2.

### Migration mapping rule

```
<slug>-v<MAJOR>           → v<MAJOR>
<slug>-v<MAJOR>.<MINOR>   → v<MAJOR>.<MINOR>
v<MAJOR>(.<MINOR>)?       → no change (idempotent)
legacy/...                → no change (preserved)
other                     → manual-needed (stderr warn, no auto-apply)
```

### Risk flags

- `migration` — data integrity. dry-run default + `.bak.<timestamp>` 백업 + idempotent 으로 mitigation.

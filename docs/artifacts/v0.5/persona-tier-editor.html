Persona Tier Editor

페르소나별 doctrine 3계층(Tier 0/1/2)을 한눈에 보고, Tier 1·Tier 2 파일을 인라인 편집한다. Tier 0 은 읽기 전용.
DESIGN ONLY · 빌드 티켓 승인 전 PO 사용자 리뷰로 회수 owner: designer surface: packages/gui 2026-06-04
이 surface 는 doctrine 의 멘탈 모델(Tier 0 = governance / Tier 1 = project / Tier 2 = personal)을 그대로 화면으로 옮깁니다. 한 페르소나의 세 계층을 좌우로 나란히 보여주어 override 스택이 한눈에 들어오고, Tier 0 은 잠금(읽기 전용), Tier 1·Tier 2 는 편집 가능이라는 경계가 시각적으로 분명해집니다.

1목표와 범위

페르소나별 doctrine 3계층 전체를 보고, Tier 1(project)·Tier 2(personal) doctrine 파일을 인라인 편집하는 GUI surface 입니다. Tier 0(persona doctrine)은 엄격히 읽기 전용 — 보기만 가능하며 명확한 잠금 표시와 함께 렌더됩니다.

범위 IN
  • 4 personas (po, designer, developer, qa) × 3 tiers (T0/T1/T2) × 계층별 N 파일.
  • 모든 계층의 모든 파일 보기 (rendered markdown).
  • T1·T2 의 *.md 편집 + 저장 (habit.md 및 bookshelf/*.md).
  • 모든 T0 파일에 명확한 잠금/읽기 전용 표시.
범위 OUT (사용자 확정 + 조사 결과)
  • T0 편집 — 절대 불가. T0(~/.productune/doctrine/...)는 SoT packages/core/doctrine/를 install.sh가 byte-identical 로 재생성하는 미러라, 직접 편집해도 조용히 덮어써집니다. 읽기 전용만이 올바른 동작입니다. (근거: ~/.productune/doctrine/persona/po/bookshelf/doctrine-editing.md §structure.)
  • non-markdown state 편집(po-state.json, usage-state.json, env 파일) — runtime state 이지 doctrine 이 아님. 다른 곳에서 참고용으로만 노출, 본 에디터 대상 아님.
  • Claude agent pointer(~/.claude/agents/<id>.md) — 기존 PersonaDefTab "spec" 에디터로 이미 편집 가능. 중복하지 않음.

2정보 구조 (IA)

데이터 형태 (2026-06-04 디스크 실측)

인벤토리는 희소하고 비대칭입니다 — 모든 페르소나가 모든 계층을 갖지 않고, 모든 계층이 bookshelf 를 갖지도 않습니다. IA 는 "habit 만", "habit + bookshelf", "빈 계층" 세 상태를 모두 자연스럽게 렌더해야 합니다.

권장 네비게이션: 페르소나 선택(rail) + 계층 3컬럼

기각한 대안:

  • 단일 깊은 트리(persona > tier > file): 사용자가 명시적으로 중시하는 T0/T1/T2 멘탈 모델을 묻어버리고, 잠금 상태가 트리 깊숙이 사라짐.
  • 계층별 탭: 항상 3개 중 2개 계층을 가림. 핵심은 한 페르소나의 override 스택(T2 personal > T1 project > T0 doctrine)을 나란히 보는 것.

채택한 레이아웃은 한 페르소나의 세 계층을 컬럼으로 나란히 놓고, 페르소나는 좌측 rail 로 전환합니다. doctrine 자체의 멘탈 모델(Tier 0/1/2 = governance / project / personal)을 그대로 반영하고, 잠금 경계를 분명히 합니다 — T0 컬럼은 시각적으로 잠겨 있고 T1/T2 컬럼은 편집 가능.

어느 컬럼에서든 파일을 선택하면 컬럼 안 인라인이 아니라 메인 에디터 패널(기존 탭 시스템 재사용)에서 열립니다. 컬럼은 컴팩트한 네비게이터로 유지하고, 편집은 MdRenderer와 textarea 가 이미 있는 풀폭 메인 패널에서 일어납니다.

4편집 어포던스와 저장 의미

T0 (read-only)

기존 ArtifactMdTab 읽기 전용 패턴을 그대로 재사용: breadcrumb + MdRenderer body + 기존 잠금 배지(lock 아이콘 + 읽기 전용). edit/preview 토글 없음, save 없음. Tier-0 컬럼 헤더에도 lock 글리프를 달아 파일을 열기 전부터 경계가 보이게 합니다.

T1 / T2 (editable)

PersonaDefTab spec-editor 인터랙션을 재사용(이미 agent spec 용으로 출시됨): Preview ⇄ Edit 토글, monospace textarea, Save / Cancel 버튼, 인라인 에러 + "saved" 확인.

  • Preview → MdRenderer (rich).
  • Edit → 방금 읽은 파일 내용으로 시드된 monospace textarea.
  • Save → 신규 IPC doctrine:writeFile(path, content). atomic tmp+rename 방식(electron/ipc/settings.ts의 persona:writeSpec과 동일).

저장이 쓰이는 위치 — 그리고 promotion-gate 질문

조사 핵심 결과: 오늘 doctrine 계층 파일에 대한 직접-쓰기 IPC 는 존재하지 않습니다. 유일한 기존 doctrine write 는 promotion gate — electron/mechanical-write.ts의 mechanicalWrite가 승인/편집된 promotion delta 를 대상(docs/<p>/habit.md, ~/.productune/<p>/bookshelf/<f>.md)에 append 합니다. 이는 agent 가 생성한 promotion 후보를 사람이 승인하는 경로입니다. persona:writeSpec은 doctrine 계층이 아니라 다른 파일(~/.claude/agents/<id>.md, agent pointer)을 씁니다.

따라서 이 기능은 T1/T2 doctrine 에 대한 최초의 human-direct full-file write 를 도입합니다. 저장 의미 두 가지(사용자 결정 필요):

Option A — direct write (v1 권장)

T1/T2 는 명시적으로 사용자 소유 계층이며, 사람이 GUI 에서 자기 project/personal doctrine 을 편집하는 것 자체가 human curation 단계입니다. 엄격한 path whitelist(resolved path 가 docs/<p>/ 또는 ~/.productune/<p>/ 안 · 확장자 .md · persona ∈ 4)와 함께 doctrine:writeFile로 직접 씁니다. 기존 memory:readFile whitelist guard(electron/ipc/settings.ts 118–128행)를 그대로 따릅니다.

Option B — promotion gate 경유

GUI 편집을 promotion 후보로 보고 동일 승인 drain 을 거치게 합니다. 더 무겁고, 사람이 이미 소유·직접 편집하는 계층에는 중복입니다. T1/T2 에는 비권장이지만, doctrine 의 저작 규칙(caps · actor-voice · leak 카테고리)이 실제 품질 게이트라는 점 때문에 함께 표기합니다.

doctrine 품질 규칙은 에디터에서 advisory 일 뿐 강제하지 않습니다. doctrine-editing.md 저작 규칙(caps: common habit ≤50 / persona habit ≤100 / bookshelf ≤100 lines · actor-voice · 5 leak 카테고리)은 doctrine 콘텐츠에 적용됩니다. 에디터는 cap 대비 non-blocking 줄 수 배지(예: habit.md — 84/100)를 표시해 초과 시 사용자가 알 수 있게 하되, 저장을 막아서는 안 됩니다. T0 만이 유일한 hard gate(lock)입니다.

충돌 / 저장 의미

  • read-time snapshot + dirty tracking. Edit 시 on-disk 내용을 캡처. Save 시 snapshot 이후 디스크가 바뀌었으면(mtime/hash 불일치 — 그 사이 agent promotion 이 append 했을 수 있음) 무조건 덮어쓰지 않고 기존 conflict modal 패턴(ConflictResolveModal.tsx)을 띄웁니다. 닫기 시 unsaved-changes 가드는 다른 곳에서 쓰는 BaseDirtyModal.tsx 재사용.
  • Atomic write(tmp + rename)로 torn file 방지.
  • 저장 범위는 whole-file replace(에디터가 전체 문서 소유) — gate 의 append 의미와 구분됩니다.
